# 首版执行计划

首版目标与范围见 [README](../../README.md#首版目标)，组件边界和部署模型见[系统架构](../design/architecture.md)。

## 执行顺序

先在单进程中跑通行情驱动的交易闭环，再接入 SimNow，扩展多策略、同机多进程、广播和跨机通信。每个节点交付可运行的功能及对应验证入口，接口与基础组件随功能实现。

| 节点 | 可运行的功能产出 | 依赖 | 验证入口 |
| --- | --- | --- | --- |
| N1 | `monod` 中的策略订阅并处理行情 | 无 | `v1_01_market` |
| N2 | `monod` 完成报单、撤单和成交回报处理 | N1 | `v1_02_order` |
| N3 | 单个做市策略根据行情更新双边报价 | N2 | `v1_03_maker` |
| N4 | `monod` 在 SimNow 上运行做市策略 | N3 | `v1_04_simnow_adapter`、`verify_simnow_monod` |
| N5 | 多个策略通过同一个账户同时交易 | N4 | `v1_05_multi_strategy` |
| N6 | `marketd`、`strategyd`、`tradingd` 在同机通过点对点消息运行交易闭环 | N5 | `v1_06_local_processes` |
| N7 | 一个行情服务通过单机广播向多个策略进程分发行情 | N6 | `v1_07_broadcast` |
| N8 | 不同机器上的业务进程通过 `relayd` 完成交易闭环 | N7 | `v1_08_remote_processes` |

验证入口由对应节点实现并交付，C++ 测试框架与运行方式遵循[项目测试约定](../../AGENTS.md#测试)。`v1_` 开头的自动化场景注册为 CTest 测试，使用断言和退出码判定结果；`verify_simnow_monod` 及后续节点的 SimNow 场景使用实际接入脚本和运行说明。固定行情和可控柜台回报用于自动化验证，各节点复用相同的业务 service 和策略实现。

## 节点交付与验收

### N1：单进程行情订阅与策略响应

**功能产出**：启动 `monod`，由行情 service 接收固定行情，策略通过 client 订阅行情并产生可核对的报价意图。

实现内容：

- 建立可构建、可运行的 `monod`，按组件组织共享库。
- 组装 container、行情 service、策略 service 及进程内 client；通过 service ID 和静态拓扑连接服务。
- 定义首版策略所需的行情字段与订阅接口，由行情 service 驱动注入的行情接入对象，完成接收、缓冲复用和订阅分发。
- 实现单业务线程的组件注册、循环调度和退出，明确行情数据的访问期。

验收方法：

1. 通过注入的行情源提供带序号的固定行情，由行情 service 接收，核对策略收到的品种、价格、数量、顺序和总数。
2. 改变行情价格，核对策略产生的报价意图随之变化。
3. 验证进程内路径通过 client 直接调用，业务处理均在同一个线程执行。
4. 场景结束后程序正常退出，无残留调度注册。

N1 按以下步骤顺序实现，每一步都保持程序可构建、可运行，并交付对应的自动化验证入口。

第二级任务的代码量上限、统计口径及拆分确认流程遵循[开发计划约定](../../AGENTS.md#开发计划)。下表为规划预算，各步新增场景纳入 N1 的 `v1_01_market` 综合验收。

| 步骤 | 可运行的功能产出 | 代码预算 | 验证入口 |
| --- | --- | --- | --- |
| N1.1 | `monod` 接收一条固定行情，经 client 交付策略并产生报价意图 | ≤450 行 | `v1_01_single_quote` |
| N1.2 | 连续处理固定行情序列，每条行情产生对应的策略响应 | ≤300 行 | `v1_01_quote_sequence` |
| N1.3 | 由 container 运行循环驱动行情和策略，处理完有限输入后退出 | ≤420 行 | `v1_01_container` |
| N1.4 | 按品种订阅行情，并在退订后停止接收 | ≤380 行 | `v1_01_subscription` |
| N1.5 | 由行情 service 内部接收行情，并按订阅分发给策略 | ≤380 行 | `v1_01_market_source` |
| N1.6 | 从静态配置加载部署信息，校验本进程的 service 组装 | ≤450 行 | `v1_01_topology` |
| N1.7 | 按目标 service ID 通过 factory 获取进程内行情 client | ≤350 行 | `v1_01_client_factory` |
| N1.8 | 在回调中退订或请求停止，安全完成退出及资源释放 | ≤400 行 | `v1_01_shutdown` |

#### N1.1：单条行情产生报价意图

**进度**：实现完成，macOS arm64 构建与自动化验证通过；Linux x86_64 验收待执行。

**交付**：一个最小可运行的 `monod`，包含行情 service、进程内行情 client 和承载单个验证策略的策略 service。验证策略以买卖盘口价格生成报价意图，通过标准输出提供可核对的业务结果。

- 建立最小 CMake 构建，接入 GoogleTest 并注册 CTest 验证入口，公共实现放入对应组件库。
- 定义单条行情及报价意图所需的最小数据类型，连接 client 接口和行情回调。
- 在 `main` 中显式创建组件，注入一条固定行情并运行完整调用路径。

**验证**：构建并启动 `monod`，核对策略收到的品种、买卖价格和数量，以及输出的报价意图价格；确认行情只交付一次，回调在调用线程执行。验收程序对业务结果作断言并返回退出码。

#### N1.2：连续行情驱动策略响应

**进度**：实现完成，macOS arm64 构建与自动化验证通过；Linux x86_64 验收待执行。

**交付**：`monod` 使用可复用的固定行情源，连续处理有限的行情序列，策略按行情变化更新报价意图。

- 为固定行情源增加逐条取数和输入结束状态，将其接入已有行情 service。
- 为行情增加验证所需的序号，在回调访问期内使用数据，使用预分配存储保留验收结果。
- 在程序组装层驱动固定源处理，输入结束后正常返回。

**验证**：输入包含价格及数量变化的序列，逐条核对字段、顺序、总数和对应报价意图；重复运行得到相同结果。覆盖空序列与最后一条行情，检查源对象复用存储时已保存的结果保持正确。

#### N1.3：container 驱动有限运行

**进度**：实现完成，macOS arm64 构建与自动化验证通过；Linux x86_64 验收待执行。

**交付**：`monod` 使用 container 的单业务线程运行循环驱动行情源，有限输入处理完成后结束运行。

- 提供调度组件接口、注册关系和循环驱动，将固定源的逐条处理接入该接口。
- 程序在初始化阶段完成组件组装和注册，通过 container 启动运行。
- 定义本步骤所需的输入结束与停止条件，使最后一条行情处理完成后退出循环。

**验证**：核对输入、回调次数和报价意图与 N1.2 一致；记录行情源及策略回调的执行线程，确认由同一线程执行。验证空输入和正常输入均能在测试时限内退出。

#### N1.4：按品种订阅与退订

**进度**：实现完成，macOS arm64 构建与自动化验证通过；Linux x86_64 验收待执行。

**交付**：策略通过行情 client 选择订阅品种，并能主动退订。

- 在行情 service 和本地 client 中维护订阅关系，处理订阅建立与取消。
- 将订阅参数接入验证策略，明确重复订阅、重复退订及无订阅者时的行为。
- 每次回调只借用本次行情数据，策略保留状态时写入自身存储。

**验证**：交错输入两个品种的行情，核对策略只收到订阅品种；在两次行情交付之间退订，确认后续行情不再进入该策略。覆盖重复操作及无订阅者的场景。

#### N1.5：行情 service 负责接收与分发

**交付**：`monod` 通过 container 调度行情 service，由 service 内部接收固定行情并按已有订阅分发，保持策略收到的行情和报价意图一致。

- 在 market 库中定义行情接入抽象，由 `examples` 中的固定行情源实现；公共库依赖接入抽象。
- 将逐次接收行情、复用接收缓冲区和订阅分发的职责归入行情 service，由 service 的调度入口推进处理。
- 程序组装层创建具体行情接入对象并注入 service，将行情 service 注册到 container。移除外置 `QuotePublisher`，将 `Publish` 的分发职责收为 service 内部实现，示例和测试通过注入行情源提供输入。
- 区分有行情、暂时无行情和输入结束，明确行情接入对象及回调数据的有效期。

**验证**：通过 container 运行行情 service，核对原固定序列的字段、顺序、订阅过滤和报价意图；空输入正常退出，最后一条行情只交付一次。行情源暂时无数据后提供新行情时，service 能继续接收，直到输入结束才完成调度。验证接收及策略回调在同一业务线程执行，缓冲区复用后已保存的快照保持正确。

#### N1.6：加载并校验静态部署信息

**交付**：`monod` 从静态文件获取 host、进程和 service 标识，并校验配置与当前程序组装的组件一致。

- 定义 N1 所需的最小拓扑字段和初始化解析路径，读取本进程及其 service 条目。
- 为本地组件建立 service ID 注册关系，检查标识重复、归属缺失及配置与组装不一致。
- 提供可运行的单进程样例配置，启动失败通过诊断和退出码表达。

**验证**：使用两组不同 service ID 的有效配置启动相同行情场景，核对业务结果一致；使用缺少必要字段、重复 ID、缺少归属进程及组装不匹配的配置，核对程序在业务运行前明确失败。

#### N1.7：通过 factory 获取本地 client

**交付**：策略初始化时按目标行情 service ID 获取 client，程序组装层提供 factory 所需的拓扑和本地实例注册关系。

- factory 根据拓扑定位目标实例，创建连接对应行情 service 的进程内 client。
- 策略通过取得的抽象 client 完成订阅、行情处理及退订。
- 明确目标不存在、service 类型不匹配和当前尚未支持的跨进程目标的失败结果；跨进程实现由 N6 接入。

**验证**：按配置中的 ID 获取目标 client，核对完整行情响应；构造错误 ID、错误类型和非本进程目标，核对失败结果。检查成功路径仍直接调用本地对象，并保持既有订阅行为。

#### N1.8：回调中的停止与退出

**交付**：策略可以在处理行情时退订或请求停止，程序完成当前处理后安全退出，解除订阅及调度注册，再销毁组件。

- 明确回调期间取消订阅及请求停止的生效边界，处理遍历中的注册变更。
- 停止行情 service 内部的接收流程，组装层按依赖关系管理 client、service、行情接入对象和 container 的使用期及退出顺序。
- 将已有场景与退出场景接入 `v1_01_market`，完成 N1 整体验收。

**验证**：在指定行情的回调中退订，核对之后不再收到行情；在指定回调中请求停止，核对程序按约定结束处理。确认停止后不再接收后续行情，无额外回调，退出前订阅和调度注册均已解除，多次运行的响应与退出结果一致。

### N2：单进程订单生命周期

**功能产出**：`monod` 中的策略通过交易 client 发出报单和撤单请求，通过回调获得执行结果，并同步查询订单状态。

实现内容：

- 组装交易 service、进程内交易 client 和可控的柜台验证适配器。
- 定义报单、撤单、订单与成交回报、状态查询接口，明确请求发出、发送失败及实际执行结果的表达方式。
- 定义调用方、交易服务、柜台订单标识的关联规则，以及回报向调用方交付的规则。
- 实现订单状态维护、查询可用性和回调分发；明确直接调用及延迟回调的数据生命周期。

验收方法：

1. 驱动报单成功、委托拒绝、撤单成功、撤单失败、部分成交及全部成交场景，逐项核对状态和回报。
2. 交错返回多个订单的回报，核对请求关联和订单标识映射。
3. 查询尚不可用的状态和已建立的状态，核对可用性及数据内容。
4. 用同步返回回报的适配器构造重入场景，验证 client 按接口约定直接交付或延迟交付，状态更新正确。

### N3：行情驱动的简单做市

**功能产出**：`monod` 中的单个做市策略根据行情维持双边报价，处理成交及撤单回报。

实现内容：

- 在策略设计中确定简单报价规则及最小状态机，连接行情 client 和交易 client。
- 验证场景使用买卖盘口生成双边报价；盘口变化时撤回需要更新的旧单，收到撤单结果后按策略规则更新报价。
- 处理未完成请求、成交和拒绝回报，避免在等待回报时重复提交相同操作。
- 在验证程序中建立行情进入到交易请求发出的单进程延迟测量。

验收方法：

1. 固定行情不变时，核对不会持续重复报单。
2. 输入价格变化，核对撤旧单、处理回报、提交新报价的顺序与价格。
3. 在改价过程中插入成交、延迟回报和拒绝回报，核对策略状态及后续报价行为。
4. 对同一组输入重复运行，订单请求序列和最终状态一致；记录单进程延迟基线。

### N4：SimNow 单进程做市

**功能产出**：`monod` 使用实际 SimNow 行情和交易接入运行做市策略。

实现内容：

- 提供 C++ 行情与交易接入实现。程序组装层通过 N1.5 定义的接口，将 SimNow 行情接入对象注入行情 service。
- 由行情 service 驱动实际行情接收和订阅分发；接入库回调交给所属 service 的业务线程处理，完成行情订阅、委托提交、撤单及回报转换。
- 定义接入就绪与策略启动的条件，提供运行所需的最小静态参数。
- 复用 N3 的策略及 client 接口。

验收方法：

1. 通过 `v1_04_simnow_adapter` 向接入实现注入可控回调，核对行情及交易回报的字段转换、标识关联和业务线程交付。
2. 通过 `verify_simnow_monod` 在 Linux x86_64 上使用有效的 SimNow 账户、接入地址和可交易合约启动程序。
3. 接收实际行情，核对策略报价与收到的行情对应。
4. 完成实际报单、撤单和成交回报处理，核对调用方订单标识与柜台回报的关联，并保留请求、回报和最终订单状态记录。

### N5：多策略共享账户

**功能产出**：一个 `strategy-service` 同时承载多个策略实例，通过同一个交易账户完成交易；同一进程也能承载多个策略 service 实例。

实现内容：

- 管理多个策略实例的初始化、行情分发、交易调用和回报归属。
- 明确 service 内的策略标识、订单归属及 client 使用方式，覆盖多策略和多调用方的标识关联。
- 交易服务统一处理共享账户的请求，向相应调用方返回回报。

验收方法：

1. 在固定场景中同时运行至少两个策略，交错产生订单、撤单及成交回报，核对每个策略仅收到自己的交易回报。
2. 分别覆盖同一策略 service 内的多个策略，以及同一进程内的多个策略 service；确认两个层次的归属均正确。
3. 使用同一品种和不同品种的固定行情，核对行情分发、订单状态和各策略查询结果。
4. 在 SimNow 上以同一账户运行至少两个策略，完成各自的报单和撤单，并核对实际成交回报的策略归属。

### N6：同机多进程点对点运行

**功能产出**：在同一台机器运行 `marketd`、一个或多个 `strategyd` 和 `tradingd`，通过共享内存点对点消息完成交易闭环。

实现内容：

- 提供业务程序各自的组装代码，复用已有 service 和 container。
- 实现进程对之间每个方向独立的共享内存 SPSC 通道，以及按 service ID 分发的 message bus。
- 实现跨进程 client、server 和消息编码，factory 根据拓扑选择调用路径。
- 实现远端 client 的初始状态获取、缓存更新和查询可用性；明确组件就绪顺序、消息保序范围、队列满和对端退出时的行为。

验收方法：

1. 通过 `v1_06_local_processes` 启动完整进程组，使用固定输入核对行情、请求、回报及最终状态。
2. 与 `monod` 使用同一组输入，核对业务结果一致；通过远端 client 的查询验证缓存随回报更新。
3. 在通道绕回、容量耗尽和对端提前退出时，核对行为符合接口约定，验收程序能够明确判定成功或失败。
4. 在独立策略进程中注入慢处理或进程崩溃，核对其余进程仍能处理自己的业务，回报不会误交付给其他策略。
5. 替换为 SimNow 接入，在同机多进程布局中完成多策略共享账户的报单、撤单和成交回报处理。

### N7：单机广播行情

**功能产出**：`marketd` 通过共享内存 SPMC 队列，将行情广播给本机多个 `strategyd`，各策略继续通过交易 client 交易。

实现内容：

- 为有广播需求的行情服务配置 SPMC 通道，接入 message bus 和行情 client。
- 定义广播订阅、消费者接入、退出及慢消费者处理规则。
- 保持策略使用的行情接口一致，点对点交易通道继续承载交易请求和回报。

验收方法：

1. 一个生产者向至少两个独立策略进程发送带序号的固定行情，核对正常消费时各接收方的数据、顺序和总数。
2. 验证单份广播数据通过 SPMC 通道供多个消费者读取。
3. 暂停一个消费者使其落后，再恢复消费，核对慢消费者处理符合约定，其他消费者仍正常处理。
4. 使用 SimNow 行情与交易接入运行多个策略，验证广播行情驱动的报价、撤单和回报归属。

### N8：跨机 relay 交易闭环

**功能产出**：至少两台机器分别运行业务进程和 `relayd`，通过共享内存及 TCP 转发完成远端行情订阅、交易请求和回报交付。

实现内容：

- 提供 `relayd` 及 relay-service，由各机器的静态拓扑指定本地 relay 的 service ID 和跨机地址。
- 实现本机业务进程到 relay、relay 之间、目标 relay 到目标业务进程的消息转发。
- 定义 TCP 消息边界、路由错误、连接失败及连接中断时的处理规则，保持原始调用方与目标 service 的标识。
- 实现跨机行情的点对点交付，复用 N7 验证过的单机广播能力。

验收方法：

1. 在两台 Linux x86_64 主机上运行完整进程组，将行情和交易服务放在一台主机，策略放在另一台主机，使用固定输入核对整个往返路径。
2. 验证远端 client 的请求回调、订单缓存及多策略回报归属，与单进程场景的业务结果一致。
3. 覆盖消息连续发送、错误路由、连接失败和中途断连，核对处理符合约定，能够识别未完成的请求。
4. 增加与行情服务同机的策略进程，验证同机广播和远端点对点行情分发同时工作，交易请求和回报归属正确。
5. 接入 SimNow，在跨机部署下运行多个共享账户的策略，完成实际报单、撤单和成交回报处理。

## 验证环境与完成条件

### 验证环境

目标平台见 [README](../../README.md#目标平台)。macOS 执行本机构建和可在本机运行的自动化场景；Linux x86_64 执行正式功能、共享内存并发及 SimNow 验收。跨机验收使用至少两台网络互通的 Linux x86_64 主机。

SimNow 场景需要有效账户、接入地址、可交易合约及可运行的交易时段。各节点交付运行参数示例与验收脚本，成交处理以实际成交回报验收；缺少环境条件或尚未收到所需回报的项目保持待验收。

### 验证入口

节点实现时同步注册自动化用例。例如，N3 的固定场景通过以下入口执行：

```sh
ctest --test-dir build -R '^v1_03_maker$' --output-on-failure
```

业务场景的自动化用例由验收程序启动对应可执行程序，施加输入、核对回报并回收进程及共享内存资源。SimNow 脚本使用实际接入参数，核对实际业务回报。验收以输入、业务回报及最终状态为依据。

### 延迟验证

从 N3 起随功能节点交付延迟测量，使用相同输入规模和明确的构建、硬件及运行条件比较不同部署：

- 单进程测量行情进入业务处理到交易请求发出的时间。
- 同机多进程增加行情到达策略、交易请求与回报往返的测量。
- 跨机记录请求与回报的往返时间，各进程内部另行测量处理时间。
- 记录负载、样本数及延迟分位数，并检查高频路径的分配和复制行为。

N3 建立单进程基线，在 N6 开始前确定各部署方式的验收负载与延迟目标，并写入性能验收用例说明。
