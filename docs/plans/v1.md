# 首版执行计划

首版目标与范围见 [README](../../README.md#首版目标)，组件边界和部署模型见[系统架构](../design/architecture.md)。

## 执行顺序

每个里程碑交付一个可独立运行和验收的功能，接口与基础组件随功能实现。实现顺序由开发依赖决定。

| 里程碑 | 可运行的功能产出 | 开发依赖 | 验证入口 |
| --- | --- | --- | --- |
| N1 | `monod` 中的策略订阅并处理行情 | 无 | `v1_01_market` |
| N2 | `monod` 完成交易处理，并查询订单与账户状态 | N1 | `v1_02_order` |
| N3 | 单个做市策略根据行情更新双边报价 | N2 | `v1_03_maker` |
| N4 | 接收 SimNow 行情，驱动验证策略产生报价意图 | N1 | `v1_04_simnow_market`、`verify_simnow_market` |
| N5 | 通过交易 client 在 SimNow 完成交易并查询账户资金和持仓 | N2 | `v1_05_simnow_trading`、`verify_simnow_trading` |
| N6 | `monod` 使用 SimNow 行情和交易接入运行做市策略 | N3、N4、N5 | `v1_06_simnow_monod`、`verify_simnow_monod` |
| N7 | 多个策略通过同一个账户同时交易 | N3 | `v1_07_multi_strategy` |
| N8 | 同机 `marketd` 向 `strategyd` 交付行情，策略产生报价意图 | N1 | `v1_08_local_market` |
| N9 | 同机策略通过 `tradingd` 交易，并查询订单与账户状态 | N7、N8 | `v1_09_local_trading` |
| N10 | `marketd` 通过单机广播驱动多个策略进程产生报价意图 | N8 | `v1_10_broadcast` |
| N11 | 通过 `relayd` 向另一台机器的策略交付行情并产生报价意图 | N8 | `v1_11_remote_market` |
| N12 | 策略通过 `relayd` 调用远端交易服务，并获得回报与账户状态 | N9、N11 | `v1_12_remote_trading` |
| N13 | 订单存储容量管理、异常接入处理、运行中对账及持久化恢复 | N2、N5 | `v1_13_storage_limits`、`v1_13_contract`、`v1_13_reconcile`、`v1_13_recovery`、`verify_simnow_reconcile` |
| N14 | 按交易所规则计算各投保属性的可平量和实际扣减量 | N2、N5、N13 | `v1_14_hedge_close` |

当前优先执行 N5.2 至 N5.6，修正重启时的全量状态重建，再进行后续交易接入与策略联调验收。

N13 可在 N2、N5 完成后推进；与跨进程部署的组合验收在 N9、N12 完成后进行。

开发依赖以所需接口实现和可控场景自动化验证通过为条件，各条功能链路按表中的依赖推进。各部署方式的 SimNow 实际验收复用 N4 的行情接入和 N5 的交易接入；等待交易时段或实际成交回报不阻塞后续里程碑的可控场景开发。

验证入口由对应里程碑实现并交付，C++ 测试框架与运行方式遵循[项目测试约定](../../AGENTS.md#测试)。`v1_` 开头的自动化场景注册为 CTest 测试，使用断言和退出码判定结果；SimNow 场景提供 `verify_simnow_` 开头的实际接入脚本及运行说明。固定行情和可控柜台回报用于自动化验证，各里程碑复用相同的业务 service 和策略实现。

## 里程碑交付与验收

### N1：单进程行情订阅与策略响应

**进度**：实现完成，macOS arm64 整体自动化验证通过；Linux x86_64 验收待执行。

**功能产出**：启动 `monod`，由行情 service 接收固定行情，策略通过 client 订阅行情并产生可核对的报价意图。

实现内容：

- 建立可构建、可运行的 `monod`，按组件组织共享库。
- 组装 container、行情 service、策略 service 及进程内 client；通过本地 service ID 注册关系，由 factory 创建连接对应实例的 client。
- 定义首版策略所需的行情字段与订阅接口，由行情 service 驱动注入的行情接入对象，完成接收、缓冲复用和订阅分发。
- 实现单业务线程的组件注册、循环调度和退出，明确行情数据的访问期。

验收方法：

1. 通过注入的行情源提供带序号的固定行情，由行情 service 接收，核对策略收到的品种、价格、数量、顺序和总数。
2. 改变行情价格，核对策略产生的报价意图随之变化。
3. 验证按 service ID 通过本地 factory 获取 client，进程内路径直接调用对应 service，业务处理均在同一个线程执行。
4. 场景结束后程序正常退出，无残留调度注册。

N1 按以下节点顺序实现，每个节点都保持程序可构建、可运行，并交付对应的自动化验证入口。

节点的代码量上限、统计口径及拆分确认流程遵循[开发计划约定](../../AGENTS.md#开发计划)。下表为规划预算，各节点新增场景纳入 N1 的 `v1_01_market` 综合验收。

| 节点 | 可运行的功能产出 | 代码预算 | 验证入口 |
| --- | --- | --- | --- |
| N1.1 | `monod` 接收一条固定行情，经 client 交付策略并产生报价意图 | ≤450 行 | `v1_01_single_quote` |
| N1.2 | 连续处理固定行情序列，每条行情产生对应的策略响应 | ≤300 行 | `v1_01_quote_sequence` |
| N1.3 | 由 container 运行循环驱动行情和策略，处理完有限输入后退出 | ≤420 行 | `v1_01_container` |
| N1.4 | 按品种订阅行情，并在退订后停止接收 | ≤380 行 | `v1_01_subscription` |
| N1.5 | 由行情 service 内部接收行情，并按订阅分发给策略 | ≤380 行 | `v1_01_market_source` |
| N1.6 | 按目标 service ID 通过本地 factory 获取进程内行情 client，完成 N1 整体验收 | ≤350 行 | `v1_01_client_factory` |

#### N1.1：单条行情产生报价意图

**进度**：实现完成，macOS arm64 构建与自动化验证通过；Linux x86_64 验收待执行。

**交付**：一个最小可运行的 `monod`，包含行情 service、进程内行情 client 和承载单个验证策略的策略 service。验证策略以买卖盘口价格生成报价意图，通过标准输出提供可核对的业务结果。

- 建立最小 CMake 构建，接入 GoogleTest 并注册 CTest 验证入口，公共实现放入对应组件库。
- 定义单条行情及报价意图所需的最小数据类型，连接 client 接口和行情回调。
- 在 `main` 中显式创建组件，注入一条固定行情并运行完整调用路径。

**验证**：构建并启动 `monod`，核对策略收到的品种、买卖价格和数量，以及输出的报价意图价格；确认行情只交付一次，回调在调用线程执行。验收程序对业务结果作断言并返回退出码。

#### N1.2：连续行情驱动策略响应

**进度**：实现完成，macOS arm64 构建与自动化验证通过；Linux x86_64 验收待执行。

**交付**：`monod` 使用可复用的固定行情源，连续处理有限的行情序列，策略按行情变化更新报价意图。

- 为固定行情源增加逐条取数和序列是否读完的查询，将其接入已有行情 service。
- 为行情增加验证所需的序号，在回调访问期内使用数据，使用预分配存储保留验收结果。
- 在程序组装层驱动固定源处理，输入结束后正常返回。

**验证**：输入包含价格及数量变化的序列，逐条核对字段、顺序、总数和对应报价意图；重复运行得到相同结果。覆盖空序列与最后一条行情，检查源对象复用存储时已保存的结果保持正确。

#### N1.3：container 驱动有限运行

**进度**：实现完成，macOS arm64 构建与自动化验证通过；Linux x86_64 验收待执行。

**交付**：`monod` 使用 container 的单业务线程运行循环驱动行情源，有限输入处理完成后结束运行。

- 提供 `Service` 接口、注册关系和循环驱动，由主循环持续调用已注册服务的 `void Run()`。
- 程序在初始化阶段完成组件组装和注册，通过 container 启动运行。
- 由程序组装层提供固定行情处理完毕的退出条件，使最后一条行情处理完成后退出循环。

**验证**：核对输入、回调次数和报价意图与 N1.2 一致；记录行情源及策略回调的执行线程，确认由同一线程执行。验证空输入和正常输入均能在测试时限内退出。

#### N1.4：按品种订阅与退订

**进度**：实现完成，macOS arm64 构建与自动化验证通过；Linux x86_64 验收待执行。

**交付**：策略通过行情 client 选择订阅品种，并能主动退订。

- 在行情 service 和本地 client 中维护订阅关系，处理订阅建立与取消。
- 将订阅参数接入验证策略，明确重复订阅、重复退订及无订阅者时的行为。
- 每次回调只借用本次行情数据，策略保留状态时写入自身存储。

**验证**：交错输入两个品种的行情，核对策略只收到订阅品种；在两次行情交付之间退订，确认后续行情不再进入该策略。覆盖重复操作及无订阅者的场景。

#### N1.5：行情 service 负责接收与分发

**进度**：实现完成，macOS arm64 构建与自动化验证通过；Linux x86_64 验收待执行。

**交付**：`monod` 通过 container 调度行情 service，由 service 内部接收固定行情并按已有订阅分发，保持策略收到的行情和报价意图一致。

- 在 market 库中定义行情接入抽象，由 `examples` 中的固定行情源实现；公共库依赖接入抽象。
- 将接收行情、复用接收缓冲区和订阅分发的职责归入行情 service。`Run()` 批量处理可用行情，当前无行情或达到内部批量上限时返回。
- 程序组装层创建具体行情接入对象并注入 service，将行情 service 注册到 container。移除外置 `QuotePublisher`，将 `Publish` 的分发职责收为 service 内部实现，示例和测试通过注入行情源提供输入。
- 行情接入接口区分有行情和当前无行情，当前无行情时继续轮询；明确行情接入对象及回调数据的有效期。
- 程序组装层向 container 提供退出条件，固定行情处理完成后结束示例运行；行情接入接口不提供输入结束状态。

**验证**：通过 container 运行行情 service，核对原固定序列的字段、顺序、订阅过滤和报价意图；空序列与正常序列均按组装层提供的条件退出，最后一条行情只交付一次。验证一次 `Run()` 能处理多条可用行情；持续有行情时达到批量上限仍能返回，后续调用继续接收。行情源当前无数据时返回，提供新行情后正常交付。验证退出条件在每次调度调用前检查，条件成立后不再调度组件；接收及策略回调在同一业务线程执行，缓冲区复用后已保存的快照保持正确。

#### N1.6：通过 factory 获取本地 client

**进度**：实现完成，macOS arm64 构建与自动化验证通过；Linux x86_64 验收待执行。

**交付**：策略初始化时按目标行情 service ID 获取进程内 client，程序组装层提供本地实例注册关系，`monod` 完成 N1 整体验收。

- 在程序组装层将行情 service 按 ID 注册到 `MarketServiceRegistry`，再将实例表注入 factory。实例表保存 `MarketService*`，factory 按 ID 查找具体实例并创建进程内 client。
- 策略通过取得的抽象 client 完成订阅、行情处理及退订。
- 明确重复 service ID 注册和目标不存在的失败结果；部署拓扑及跨进程调用路径选择由 N8、N9 实现。
- 将 factory 场景与 N1.1—N1.5 的既有场景纳入 `v1_01_market`，完成 N1 整体验收。

**验证**：向本地实例表注册多个行情 service 实例，注入 factory 后按不同 ID 获取 client，核对订阅和行情回调连接到对应实例；构造重复注册和不存在的 ID，核对失败结果。使用不同实例表创建 factory，核对查找使用注入的注册关系；实例表与 factory 销毁后，已创建的 client 仍能访问存活的目标 service。运行 `monod` 及 N1 的全部自动化场景，确认 client 直接调用本地对象，订阅、行情字段、顺序、报价意图及正常退出保持正确。

### N2：单进程交易与账户状态

**进度**：N2.1—N2.12 已实现，macOS arm64 自动化验证通过；Linux x86_64 验收待执行。

**功能产出**：`monod` 中的策略通过交易 client 发出报单和撤单请求，交易 service 统一检查与预占账户资金，通过回调交付执行结果，并提供订单、账户资金和持仓查询。

实现内容：

- 组装交易 service、进程内交易 client 和可控的柜台验证适配器；适配器通过注册的 Callback 交付回报。
- 定义报单、撤单、订单与成交回报、状态查询接口，明确请求发出、发送失败及实际执行结果的表达方式。
- 通过可控 adapter 验证各交易接口的校验、发送失败及重复和迟到回报处理。
- 由 caller 生成 YQuant 内部统一 `OrderId`，使用 caller service ID 和该 service 共享的单调序号保证单次运行期间不冲突。账户与策略作为订单归属保存，适配器维护统一 ID 与柜台订单标识的映射。
- 实现订单状态维护、查询可用性和回调分发；明确直接调用及延迟回调的数据生命周期。
- 程序启动时与柜台同步一次资金和持仓，建立账户本地基准；后续运行期间通过交易事件更新本地数据，由交易 client 提供缓存类查询并表达可用性。
- 按账户统一检查下单资金并预占，随发送结果、拒单、撤单和成交调整本地资金记录；同一账户的策略共享可用资金和占用记录。
- 按订单和成交事件维护账户持仓与平仓冻结；运行中对账、差异核实与持久化保存统一由 N13 实现。

验收方法：

1. 驱动报单成功、委托拒绝、撤单成功、撤单失败、部分成交及全部成交场景，逐项核对状态和回报。
2. 用不同 caller 的相同序号构造不同 `OrderId`，交错返回回报，核对统一 ID、柜台标识映射及账户和策略归属；核对同一 caller 跨策略、账户和目标交易服务生成的 ID 不重复。
3. 查询尚不可用和已建立的订单、资金及持仓状态，核对可用性及数据内容；资金和持仓在启动阶段以完整快照建立，核对零资金、空持仓及后续交易驱动的本地更新。
4. 验证 adapter 在报单调用期间不触发回调，后续调度时交付回报；业务回调中提交新请求时，通知顺序和状态更新正确。
5. 交错提供不同账户的资金和持仓数据，核对查询结果不串账户；共享同一账户的策略在同一更新完成后获得一致的账户状态。
6. 注入发送失败、迟到及重复回报，核对已实现的订单状态、资金与持仓查询及业务通知。
7. 交错执行共享账户的报单、发送失败、拒单、撤单和成交，核对检查金额及占用变化；停止柜台资金查询后，核对本地资金不会重复扣减或释放，余额不足的请求不会发送。
8. 启动同步后，通过共享账户的开平仓、部分成交及撤单核对本地持仓与冻结变化；交错重复及迟到回报，核对变化只计入一次，运行期不依赖柜台快照刷新。

N2 按以下节点顺序实现。代码量统计与拆分流程遵循[开发计划约定](../../AGENTS.md#开发计划)，各节点的自动化场景纳入 `v1_02_order` 综合验收。

N2.10—N2.12 采用启动一次同步、运行期本地记账的模型，实施前在[交易设计](../design/trading.md)中细化初始化与回报的衔接、资金计算及持仓冻结口径。N2.7—N2.9 的交付记录保留原有范围；N2.10 将实际运行及对应测试调整为启动同步，运行期迟到快照不改变本地状态；运行中对账及持久化模型由 N13 设计和实现。

各功能节点实现前，在[交易设计](../design/trading.md#接入异常处理)中细化对应的异常场景与处理规则，说明触发条件、已知事实与尚未收到的业务结果、状态变化、业务通知、查询可用性及后续处理。对应节点同时交付正常与异常路径的实现和可执行验证；实现中发现的新边界场景同步补入设计与验收。

- 处理未完成请求、成交和拒绝回报，避免在等待回报时重复提交相同操作。
- 在验证程序中建立行情进入到交易请求发出的单进程延迟测量。

验收方法：

1. 固定行情不变时，核对不会持续重复报单。
2. 输入价格变化，核对撤旧单、处理回报、提交新报价的顺序与价格。
3. 在改价过程中插入成交、延迟回报和拒绝回报，核对策略状态及后续报价行为。
4. 对同一组输入重复运行，订单请求序列和最终状态一致；通过 `monod --maker` 和 `v1_03_maker_monod` 核对完整请求序列与最终挂单，记录[单进程延迟基线](../benchmarks/maker.md)。

### N5：SimNow 交易与账户查询

**功能产出**：`monod` 通过 `TradingClient` 向 SimNow 报单和撤单，收到归属正确的委托、撤单和成交回报，并能查询订单、资金和持仓。SimNow adapter 负责柜台字段转换和回报交付，资金与持仓仍由 N2 的交易 service 在业务线程维护。

按 N5.1 → N5.9 顺序实现。各节点交付独立的 CTest 用例，统一使用标签 `v1_05_simnow_trading`。各节点均以 450 行为代码预算，统计与拆分遵循[开发计划约定](../../AGENTS.md#开发计划)。

#### N5.1：交易接入与账户登录

**进度**：实现完成。macOS arm64 已验证交易动态库加载；普通及 ASan/UBSan 构建均通过全部 35 项 CTest，包含 `v1_05_trader_login`。macOS arm64 已通过[个人模拟账户真实登录验收](../verification/simnow-trader-login.md)，Linux x86_64 运行待验收。

**交付**：`monod` 加载与目标平台匹配的 CTP 交易动态库，使用个人模拟账户连接交易前置，完成前置要求的认证和登录，并输出登录结果。SDK 回调通过 adapter 交给业务线程。登录成功后，账户仍等待启动同步。

**验证**：`v1_05_trader_login` 使用可控 SDK 验证连接、登录成功、拒绝、超时以及断连与重连通知。仅收到成功登录回报时，账户未就绪，提交订单不会调用柜台报单接口。

#### N5.2：启动资金与持仓快照

**进度**：macOS arm64 普通构建和 ASan/UBSan 构建均通过全部 36 项 CTest，已完成[真实账户的空仓快照查询](../verification/simnow-trader-login.md#启动快照)。Linux x86_64 运行待验收。

**交付**：登录后串行查询账户资金和全量柜台持仓，保留账户资金、持仓数量、成本、保证金及冻结字段。两项查询均完整且通过校验后发布只读快照。交易就绪在 N5.6 验收。

**验证**：通过 `v1_05_startup_snapshot` 核对多行持仓与有效空仓，覆盖缺失资金、错误账户、流控、超时、断连、重试及迟到回报。通过 `monod` 查看快照收集结果。

#### N5.3：合约乘数与计费参数

**进度**：macOS arm64 已通过 `v1_05_contract_terms` 和[真实账户 TF2612 费率查询](../verification/simnow-trader-login.md#合约计费参数)。Linux x86_64 运行待验收。

**交付**：取得指定合约的乘数、保证金率及开平手续费，转换为本地资金计算参数。

**验证**：注入已知合约和费率，核对一笔订单的资金需求；缺少参数时报告合约及缺项。

#### N5.4：恢复柜台订单与成交记录

**交付**：清空本地运行状态后，从柜台重建订单、成交及标识关联。已知归属的订单保留归属，未知归属的订单可识别、可查询，新订单标识不与历史订单冲突。

**验证**：恢复两个策略的历史记录和一笔未归属挂单；重复成交不产生第二条记录，新旧订单分别关联到正确的后续回报。

#### N5.5：恢复挂单的资金与持仓冻结

**交付**：确定今仓和昨仓各自的成本、占用保证金及冻结量。柜台汇总行不足以区分今昨仓时，用持仓明细核实。将历史挂单的未成交量关联到快照中的资金预占和今昨仓冻结。核实后沿用已有占用，无法核实时报告原因。

**验证**：恢复带非零冻结的账户，使挂单部分成交后撤销余量，逐项核对预占、持仓成本和可平量，验证无二次冻结或提前释放。

#### N5.6：启动回报衔接与策略接管

**交付**：核对各项启动查询与期间新增回报的覆盖边界；完整基准建立后开放业务查询及报单，策略可以接管已有挂单继续报价。启动失败支持重试，运行中对账与持久化恢复由 N13 交付。

**验证**：运行 `v1_05_account_startup`，通过可控 SDK 和 `monod` 验证同步期间的成交无重复或遗漏，多策略接管不串单、不重复报价，未归属订单不误交回报。核对缺行或无法关联时保持未就绪，成功后停止启动查询并忽略迟到快照。

#### N5.7：限价报单与委托回报

**交付**：使用指定账户、合约、方向、开平、价格和手数，通过 client 发出限价单。adapter 将原始 `OrderId` 与柜台请求及委托标识关联，使早期拒单和后续接受回报都能找到原调用方。

**验证**：`v1_05_submit` 捕获 SDK 请求并核对字段；分别注入确定未发送、发送成功后接受、异步拒单及重复回报。验证调用期间不触发业务回调，订单查询和 listener 归属正确；资金不足时不发送，发送失败或拒单后释放对应预占。

#### N5.8：撤单与剩余占用释放

**交付**：通过 client 撤销一笔已发送委托。adapter 将撤单回报关联到原订单及本次撤单尝试，并在确认撤销时交付最终累计成交量。

**验证**：`v1_05_cancel` 覆盖撤单发送失败、柜台拒撤、成功及重复回报。以 5 手平仓单最终成交 2 手、成交明细晚于撤单确认为例，核对只释放未成交 3 手对应的资金预占和持仓冻结；撤单失败则保留原占用。

#### N5.9：成交记账与端到端验收

**交付**：将实际成交转换为携带原始订单 ID、完整成交标识、成交价及数量的回报；通过 N2 的成交去重和记账路径更新订单、资金与持仓。

**验证**：`v1_05_fills` 交错交付部分成交、全部成交、重复明细、累计委托回报及撤单后的迟到明细，核对每笔成交只通知、记账一次，查询结果与预期的资金、持仓及冻结变化一致。

**真实验收**：运行 `verify_simnow_trading`，使用有效个人模拟账户和可交易合约，核对初始账户数据，提交限价单，收到委托确认后撤单，并按原订单标识核对最终状态。实际成交单独核对成交价、数量、策略归属及本地账户变化；未收到真实成交时保留该项待验收。运行中与柜台对账、重连核实及持久化恢复由 N13 交付。

### N7：多策略共享账户

**功能产出**：一个 `strategy-service` 同时承载多个策略实例，通过同一个交易账户完成交易；同一进程也能承载多个策略 service 实例。

实现内容：

- 管理多个策略实例的初始化、行情分发、交易调用和回报归属。
- 复用 N2 确定的标识作用范围、订单归属和回报交付规则，实现多个策略实例的 client 使用及回报分发。
- 交易服务统一处理共享账户的资金检查与预占、持仓检查与冻结和交易事件引起的账户变化，向相应调用方返回回报。
- 向共享账户的策略提供同一份账户资金和持仓状态，按账户维护接入数据的更新及查询可用性。

验收方法：

1. 通过 `v1_07_multi_strategy` 在固定场景中同时运行至少两个策略，交错产生订单、撤单及成交回报，核对每个策略仅收到自己的交易回报。
2. 分别覆盖同一策略 service 内的多个策略，以及同一进程内的多个策略 service；确认两个层次的归属均正确。
3. 使用同一品种和不同品种的固定行情，核对行情分发、订单状态和各策略查询结果。
4. 初始账户数据尚未就绪时，各策略查询均返回不可用；同一资金或持仓更新完成后，各策略查询到相同的账户快照。更新另一账户的数据不会改变共享账户的查询结果。
5. 在 SimNow 上以同一账户运行至少两个策略，完成各自的报单和撤单，并核对实际成交回报的策略归属；核对各策略查询到相同的本地资金和持仓状态。
6. 在可控场景中让多个策略交错申请超过账户可用资金的订单，核对账户统一预占；发送失败、拒单及剩余委托撤销后，其他策略能够使用按规则释放的资金，重复回报不增加可用资金。
7. 让多个策略申请平仓同一份持仓，核对统一冻结、成交扣减及剩余冻结释放；交错交易回报，核对各策略读取相同的本地持仓及可用性，不能重复使用可平数量。

### N9：同机跨进程交易

**功能产出**：同机策略通过 `tradingd` 报单、撤单，接收订单及成交回报，并同步查询 client 缓存中的订单、账户资金和持仓状态。

实现内容：

- 增加 `tradingd` 的组装代码，复用 N8 的静态拓扑、共享内存通道和 message bus。
- 实现跨进程交易 client/server 和消息编码，扩展交易 client factory，保留调用方、订单及策略归属。
- 实现远端订单、账户资金和持仓缓存的初始状态获取、更新及查询可用性；service 将本地账户状态以完整快照发布给远端 client，保留账户归属。
- 由目标交易 service 统一执行账户资金检查与预占、持仓检查与冻结，远端 client 缓存用于查询；本地与远端请求共用账户资金与持仓记录。
- 限制远端订单缓存和请求关联存储，明确缓存回收后的查询可用性；与服务端订单回收及历史查询的组合场景在 N13.1 验收。
- 明确回报顺序、队列满及对端退出对未完成请求的影响。
- 分别传递进程通信异常和柜台接入异常，保留已发送请求的关联、账户可用性，远端 client 传递交易 service 的状态；与柜台异常处理和恢复的联动在 N13.2 验收。
- 将 N7 的多策略与 N8 的跨进程行情链路接入，运行完整的同机多进程交易场景。

验收方法：

1. 通过 `v1_09_local_trading` 运行策略和交易进程，提交报撤单请求并交错注入回报，核对请求关联、策略归属及订单状态与 N2 一致。
2. 在各类缓存尚不可用、收到完整初始状态和后续更新后分别查询，核对订单、资金及持仓内容与 service 对应状态一致。核对零资金、空持仓、刷新后的旧持仓移除及多账户隔离，查询不暴露部分账户快照。
3. 联合 `marketd`、多个策略实例和 `tradingd` 运行固定场景，核对业务结果与单进程多策略场景一致。
4. 在独立策略进程中注入慢处理或进程崩溃，核对其他策略仍能处理自己的业务，回报不会误交付；交易进程提前退出时能够识别未完成请求。
5. 替换为 SimNow 行情与交易接入，在同机多进程布局中完成多策略共享账户的报单、撤单和成交回报处理，并核对远端资金及持仓查询结果与目标 service 的本地状态一致。
6. 使用较小缓存容量重复交易，核对策略进程的订单缓存及请求关联存储受限；覆盖容量不足和空间复用，核对缓存回收后的查询结果与可用性。
7. 分别中断策略与交易进程间通信、交易进程与柜台间连接，核对未确认状态、回报归属及缓存可用性；重复交付不能造成重复报单或重复成交累计；柜台断连后需核实才能恢复的路径由 N13 验收。
8. 让多个策略进程使用存在延迟的资金及持仓缓存向同一账户报单，核对目标 service 按统一账户记录检查资金及可平数量；回报重传不会重复扣减或释放资金、重复累计持仓或冻结。

验收方法：

1. 通过 `v1_11_remote_market` 在两台 Linux x86_64 主机上运行行情、策略进程和两端 relay，发送固定行情，核对订阅、行情内容及报价意图与 N8 一致。
2. 连续发送消息，核对消息边界与顺序；构造错误路由、连接失败和中途断连，核对行为符合通信约定。
3. 接入 SimNow 行情，核对另一台机器上的验证策略收到行情并产生对应报价意图。

### N12：跨机交易

**功能产出**：策略通过两端 `relayd` 调用另一台机器上的交易服务，完成报撤单、回报处理，并同步查询 client 缓存中的订单、账户资金和持仓状态。

实现内容：

- 将 N9 的交易 client/server 及订单、账户资金和持仓缓存接入 N11 的 relay 路径，配置交易 service 的跨机路由。
- 完整传递统一 `OrderId`、原始调用方和策略归属，明确连接中断时未完成请求的识别方式。
- 组装跨机行情与交易链路，运行多策略共享账户的完整场景。

验收方法：

1. 通过 `v1_12_remote_trading` 在两台 Linux x86_64 主机上提交报撤单请求并交错返回回报，核对关联、策略归属和缓存状态与 N9 一致。
2. 在请求发出后中断连接，核对未完成请求能够被识别，已收到的回报和订单状态不会错误关联。
3. 通过跨机路径传递 service 发布的资金与持仓初始视图及交易驱动的后续更新，核对数据未就绪、有效零资金、空持仓、完整快照替换及多账户隔离，与 N9 的查询结果一致。
4. 使用与单进程相同的固定输入运行跨机多策略场景，核对订单请求、回报及最终状态一致；各策略收到同一账户更新后，查询到相同的资金和持仓快照。
5. 接入 SimNow 行情与交易，在跨机部署下运行多个共享账户的策略，完成实际报单、撤单和成交回报处理，并核对远端资金及持仓查询结果与目标 service 的本地状态一致。
6. 经 relay 路径执行 N9 的容量边界与空间复用场景，核对订单保留、查询及回报处理结果一致。
7. 经 relay 路径复用 N9 的通信中断与柜台异常场景，核对不同故障来源下的已保存订单状态及本地状态保留行为一致。
8. 经 relay 路径复用 N9 的共享账户资金与持仓检查、预占及冻结场景，核对本地及跨机调用方共用同一份账户记录，缓存延迟与消息重复不导致超额预占或重复使用可平持仓。

### N13：运行中对账与持久化恢复

**功能产出**：交易 service 在运行期间与柜台核对订单、资金和持仓，处理差异并恢复可用性；持久化保存交易与账户状态，进程重启后恢复并经柜台核实继续交易。

实现内容：

- 按 N13.1 限制订单链路的内存使用，使终态记录回收后仍能查询历史订单、识别迟到回报；按 N13.2 验证接入故障、对账与恢复期间的交易契约。
- 对账：定义运行中主动核对及重连后的触发、执行责任与请求契约，获取订单、成交、资金及持仓数据。核实未确认订单、补齐缺失回报，保留来源和关联，处理外部交易及非交易资金变动造成的差异。
- 合并：明确快照覆盖订单、成交和资金变化的依据，保留尚未被覆盖的本地影响；处理查询与交易交错、重复、迟到及不完整结果，避免重复入账、冻结或释放。刷新轮次和返回顺序不能直接证明业务覆盖关系。
- 差异处理：确定订单、资金和持仓各类差异的修正规则、查询可用性及报单条件；核实失败时保留事实并支持重试，成功后恢复。资金和持仓使用一致的订单及成交核实结果。
- 持久化：保存订单与标识关联、成交去重依据、资金与持仓状态、占用及冻结，以及恢复需要的事件和处理进度。明确持久化边界、写入失败处理及崩溃一致性；存储格式和实现方案在本里程碑细化。
- 恢复：从持久化数据重建状态，识别发送结果未确认和尚未完成的请求；与柜台核实后恢复交易，不自动重报未确认请求，不重复应用已保存成交。将持久化恢复与 N5.2 至 N5.6 的柜台状态重建统一为明确的启动流程。
- 接入与部署：在 SimNow 上落实实际查询和回报语义；对账及持久化由账户所属 trading service 统一执行，向本地及远端 client 提供一致结果。

验收方法：

1. 通过 `v1_13_reconcile` 注入本地缺失订单或成交、资金差异、持仓和冻结差异，验证差异识别、核实、修正和恢复；对账无差异时状态不变。
2. 交错查询与报单、撤单、成交回报，分别提供已覆盖和未覆盖本地变化的资金、持仓快照，核对每笔影响只应用一次；失败、旧结果及重试不丢失事实或提前释放占用。
3. 模拟断连及重连，核对未确认订单不会自动重报，补齐柜台事实后资金与持仓一致，满足恢复条件后新请求可以发送。
4. 通过 `v1_13_recovery` 在请求发送、事件保存及账户更新等边界中断进程并重启；验证订单可查询、关联和去重有效、资金及持仓恢复正确。覆盖写入失败、末尾记录不完整和重复重放，无法完成恢复时不得报告交易就绪。
5. 通过 `verify_simnow_reconcile` 完成实际订单、资金及持仓查询和核对，并验证重连及持久化恢复；记录实际柜台的快照覆盖依据和验收结果。
6. N9、N12 完成后复用上述场景，核对同机与跨机 client 获得一致的状态及可用性；通过 `monod` 和多进程验收程序输出差异、恢复进度及最终结果。

#### N13.1：订单存储容量管理

**代码预算**：≤450 行。

**交付**：`monod` 在设定的订单存储内存预算内完成交易处理；容量不足时返回明确结果，已经接收的订单继续处理回报并可查询。

- 为 service 和 adapter 中订单相关存储设置可核对的容量边界，覆盖订单及索引、资金预占、持仓冻结及未确认记录、撤单关联、柜台标识映射、查重与成交去重信息、请求关联、待通知回报及接入交接缓冲。
- 释放已经完成且不再被引用的请求关联与通知数据，复用存储空间。实现前细化终态订单及其关联信息的保留、回收条件和历史查询方式，保持本次运行全部已建立订单可查询，并保证迟到与重复回报仍按原订单处理。
- 在接受新请求前检查所需容量，为已经接收的请求保留后续处理空间；容量不足时按请求契约返回失败，不能覆盖已有记录或静默丢弃回报。回收后有足够容量时恢复接收。
- 明确接入回报突发、交接缓冲耗尽或已无法保证完整接收时的账户状态与诊断行为，保留未确认信息，不能将信息缺失解释为订单已完成。

**验证**：通过 `v1_13_storage_limits` 使用较小预算重复报单、撤单及完成订单，核对订单相关存储的容量和已分配字节数受限；达到边界时，检查新请求的失败结果及已有订单的后续处理。反复执行校验失败、发送失败和请求完成场景，核对可回收数据不会随请求次数积累，并验证回收出足够空间后新请求能继续执行。检查容量不足而被拒绝的请求不遗留资金预占，记录回收不提前释放未确认占用。注入回报突发和交接缓冲耗尽，核对账户可用性、未确认状态及诊断符合规则。查询早期订单，注入迟到及重复回报、重复 `OrderId`，核对查询、归属、成交去重和通知顺序符合契约。若细化后的保留方案涉及终态记录回收或转存，补充验证处理前后的查询、查重及迟到回报。

#### N13.2：异常接入事件处理与综合验收

**代码预算**：≤450 行。

**交付**：Trading 能处理异常接入事件，在账户断连时保留订单与本地账户状态，联合验证容量、对账与持久化恢复后的交易行为。

- 沿用 N2.1—N2.3 确定的标识和接口规则，验证交错回报的请求关联与策略归属。
- 扩展可控适配器，注入未知或缺失订单标识、账户不符、非法字段及矛盾状态，落实各类事件的处理与诊断；异常数据不能误关联或覆盖已有订单。
- 按账户处理接入不可用及连接变化，保留已发送请求和本地占用；状态完整性无法确认时不恢复新报单。重连后通过柜台对账核实未确认状态，再按恢复条件开放交易。
- 验证报单调用期间不触发回调，并在业务回调中提交新请求，核对回调时机、处理顺序和数据生命周期；交错提供延迟通知和后续回报，验证同一订单的通知顺序。
- 核对资金及持仓更新按账户隔离，共享同一账户的调用方查询同一份账户状态。
- 联合验证启动同步、资金与持仓检查和交易事件驱动的本地更新；断连及未确认订单不导致错误释放，同一账户的多个调用方不能重复使用同一份可用资金或可平持仓。
- 复用 N2 的 `v1_02_order` 回归场景，通过 `v1_13_contract` 交错执行异常回报、容量耗尽、断连对账及重启恢复，验证恢复前后使用同一交易契约。

**验证**：不同 caller 使用相同序号时，交错回报仍正确关联；同一完整 `OrderId` 换账户或策略重复提交仍被拒绝，原订单及回报接收方保持不变。撤单和订单查询的账户或策略不匹配时，不操作原订单；不同账户的相同柜台标识仍能关联到各自的统一订单 ID。交错注入有效回报和各类异常事件，核对状态、通知、诊断和查询可用性。模拟一个账户断连及连接恢复通知，核对在途请求与占用保留、已发送请求不自动重报、未经核实不恢复新报单，其他账户仍可正常交易。回报交付与嵌套调用遵循接口契约；运行 `v1_13_contract`，核对对账和持久化恢复后回报不重复入账，未确认订单不自动重发。

### N14：按交易所规则处理平仓的投保属性

**功能产出**：交易 service 根据合约所属交易所选择平仓规则。订单保留报入的投保标志（`HedgeFlag`）；可平量检查、委托冻结、成交扣减和撤单释放使用该交易所允许扣减的持仓。开仓和持仓查询保留各自的投保属性。

实现时逐一核实目标交易所对投机、套利和套保持仓的平仓规定，在交易设计中记录规则来源与适用范围。对要求属性匹配的交易所，只使用匹配持仓；对规定扣减顺序的交易所，按其顺序分配，并结合今昨仓约束计算每类持仓的数量。使用实际扣减的持仓计算平仓盈亏和释放保证金，不能仅凭报单标志推断被平持仓的属性。

**验证**：通过 `v1_14_hedge_close` 在两种规则下重放同一场景：账户有同一合约的 1 手投机多仓和 1 手套保多仓，以套保标志卖平 1 手。严格匹配场景应扣套保仓；投机优先场景应扣投机仓并保留套保仓。再覆盖套利持仓、部分成交后撤单和可平量不足，逐项检查冻结、扣减、释放及资金变化，并用 N13 对账核实各属性的剩余持仓。

## 验证环境与完成条件

### 验证环境

目标平台见 [README](../../README.md#目标平台)。macOS 执行本机构建和可在本机运行的自动化场景；Linux x86_64 执行正式功能、共享内存并发及 SimNow 验收。跨机验收使用至少两台网络互通的 Linux x86_64 主机。

各里程碑分别记录实现与自动化验证进度，以及 SimNow 实际验收进度。SimNow 场景需要有效账户、接入地址、可交易合约及可运行的交易时段。各里程碑交付运行参数示例与验收脚本，成交处理以实际成交回报验收；缺少环境条件或尚未收到所需回报时，对应的 SimNow 验收项保持待验收。

### 验证入口

里程碑实现时同步注册自动化用例。例如，N3 的固定场景通过以下入口执行：

```sh
ctest --test-dir build -L v1_03_maker --output-on-failure
```

业务场景的自动化用例由验收程序启动对应可执行程序，施加输入、核对回报并回收进程及共享内存资源。SimNow 脚本使用实际接入参数，核对实际业务回报。验收以输入、业务回报及最终状态为依据。

### 延迟测量

从 N3 起随功能里程碑交付延迟测量，使用相同输入规模和明确的构建、硬件及运行条件比较不同部署：

- 单进程测量行情进入业务处理到交易请求发出的时间。
- 同机多进程增加行情到达策略、交易请求与回报往返的测量。
- 跨机记录请求与回报的往返时间，各进程内部另行测量处理时间。
- 记录负载、样本数及延迟分位数，并检查高频路径的分配和复制行为。

N3 建立单进程基线，N8—N12 沿用相同测量口径记录和比较结果。性能目标及数值验收门槛暂不设定。
