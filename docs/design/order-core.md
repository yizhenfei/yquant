# 订单核心与请求执行

`trading::OrderCore` 管理单笔订单的业务状态，接收事件并产生动作命令。`trading::OrderRequestExecutor` 执行新单和撤单请求，管理排队、发送、响应及结果不确定的请求。实时处理、事件回放和单元测试共用各自的转换规则。

## 职责与所有权

| 对象 | 职责 |
| --- | --- |
| `OrderCore` | 订单生命周期、数量、未决撤单尝试及回报位置；业务事件校验和动作生成 |
| `OrderRequestExecutor` | 待发送队列、in-flight 请求表、发送调度、响应关联、超时及本地请求结束 |
| `TradingEngine` | 本地受理、编号分配、账户和索引处理及跨组件事务提交 |
| `TradingAdapter` | 请求发送和柜台回报归一化 |
| 策略侧交易服务 | 接收已提交的订单和账户视图，分发策略回调 |

引擎按值持有订单核心，并持有使用预分配存储的请求执行器。订单核心不调用执行器、适配器、账户、时钟或策略，也不查询外部可变状态。执行器根据核心产生的命令安排请求，由引擎协调提交后执行外部操作。

权限、账户类型与标的适配、资源预占及全局容量检查由引擎完成。本地受理事件表达这些检查及预占准备已成功；订单、执行器请求记录和预占在同一事务中发布。受理失败不建立订单核心，不消耗请求身份。

公共标识、计量及快照沿用[委托模型](trading.md#委托模型)，业务规则集中维护在[交易模块设计](trading.md)。本文维护订单核心与请求执行器的状态、输入输出及提交边界。

## 订单核心

### 业务状态

| 生命周期 | 含义 |
| --- | --- |
| `PendingNew` | 本地已受理，尚未确认柜台受理；请求可以仍在排队，也可以已经发送 |
| `Working` | 柜台已受理或已有部分成交，仍有剩余数量 |
| `Filled` | 全部成交 |
| `Canceled` | 剩余数量已取消，已有成交保持有效 |
| `Rejected` | 柜台拒绝新单 |

部分成交通过数量字段表达，生命周期保持 `Working`。创建前的对象不提供有效订单快照，该初始化阶段不增加 `model::OrderState` 枚举项。

核心还保存是否有未结束的撤单尝试及其 ID。`cancel_pending` 表示该次业务请求未结束，不区分排队和发送；最近一次撤单 ID 在尝试结束后保留。只有 `Working` 且没有未决撤单的订单可以受理新的撤单请求。

核心保存原始委托属性、`ClientOrderId`、`AdapterOrderId`、累计成交量、剩余量及最近接受的柜台回报序号和时间。`StrategyOrderId` 在核心快照中保持为零，由网关路由层补充。价格步长、数量步长及柜台主动撤单许可作为不可变规则按值保存。

核心不保存新单或撤单的发送阶段、请求响应期限、发送队列位置、资源预占金额或账户余额。全部成交后，订单保持 `Filled`；未决撤单由执行器根据请求进度取得柜台结果或产生本地结束事件。

### 输入事件

核心事件自持订单身份、载荷及处理时间。撤单事件携带具体尝试 ID。柜台事件使用 `model::TradingEvent` 载荷，本地结果使用独立事件类型。

| 事件 | 核心状态变化 | 动作 |
| --- | --- | --- |
| 本地订单受理 | 建立订单并进入 `PendingNew` | `SubmitOrder` |
| 本地撤单受理 | 验证可撤性，登记尝试 ID，设置 `cancel_pending` | `CancelOrder` |
| 新单发送前取消完成 | `PendingNew → Canceled`，剩余量归零，柜台回报序号保持为零 | 释放剩余资源，发布 `CanceledBeforeSend` 更新 |
| 撤单未发送而在本地结束 | 验证订单已终结并核对当前尝试 ID，清除 `cancel_pending`，保持原终态 | 发布 `CancelNotSent` 更新 |
| 柜台受理 | `PendingNew → Working`，保存首次获得的适配器订单 ID | 发布订单更新 |
| 迟到受理 | 保留 `Working`、`Filled` 或 `Canceled`，推进回报位置 | 不重复发布订单更新 |
| 柜台拒单 | 合法的待受理订单进入 `Rejected`，剩余量归零 | 释放剩余资源，发布订单更新 |
| 柜台成交 | 更新累计量和剩余量，进入 `Working` 或 `Filled` | 应用本笔成交，发布订单更新 |
| 柜台撤单成功 | 结束匹配尝试，进入 `Canceled`，剩余量归零 | 释放剩余资源，发布订单更新 |
| 柜台撤单拒绝 | 结束匹配尝试，保留生命周期及剩余量 | 发布包含撤拒原因的更新 |
| 柜台主动撤单 | 规则允许且无本地未决撤单时，待受理或工作中订单进入 `Canceled` | 释放剩余资源，发布订单更新 |

核心不接收发送调度、发送失败或请求超时事件。请求是否已经尝试发送、能否在发送前取消，由执行器验证。核心应用新单发送前取消结果时，仍须校验订单处于 `PendingNew`，没有成交、已接受的柜台回报或未决撤单。

首条有效柜台事件可以是成交，无须等待独立受理通知。[FIX 订单状态规范](https://www.fixtrading.org/wp-content/uploads/download-manager-files/Order-State-Changes.pdf)第 4 章包含首条回报直接为部分或全部成交的流程。当前 CTP 桥在首笔成交前生成受理事件，其输出保证受理先于成交。具体接口的顺序由适配器归一化，核心统一支持有效成交隐含受理及迟到受理。

首次获得 `AdapterOrderId` 属于核心字段更新。受理、成交或柜台主动撤单等合法回报都可能首次提供该身份。引擎在提交时验证全局唯一性并建立索引，核心不产生绑定命令。

### 动作命令

| 命令 | 载荷与执行语义 |
| --- | --- |
| `SubmitOrder` | 订单身份及原始请求；交给执行器建立一个新单请求 |
| `CancelOrder` | 订单身份、适配器订单 ID 及撤单请求 ID；交给执行器建立该次撤单请求 |
| `ApplyExecution` | 本笔成交及转换前后的订单信息；准备成交记录、账户记账和相应冻结资源消耗 |
| `ReleaseRemainingReservation` | 订单身份及终态原因；准备释放尚未被成交消耗的委托资源 |
| `PublishOrderUpdate` | 快照、结果种类、关联撤单 ID 及原因；提交后发布 |

`SubmitOrder` 和 `CancelOrder` 表达业务操作，由执行器决定排队与发送时机；命令产生时不直接触发适配器调用。

成交资源消耗由 `ApplyExecution` 处理，全部成交不额外释放一次剩余资源。`CancelNotSent` 只结束未发出的撤单尝试，不释放订单资源，也不把 `Filled` 改为 `Canceled`。资源释放规则见[预占与成交](trading.md#预占与成交)。

命令携带自持有界数据，不包含组件指针或回调，使用有界存储返回。成交的通知数据随 `ApplyExecution` 提供，提交后按[落账与回调顺序](trading.md#落账与回调顺序)先通知订单更新，再通知成交。

### 校验与应用结果

核心校验单笔订单身份、当前撤单尝试 ID、适配器订单身份、事件字段和时间、价格及数量约束、回报连续性、累计成交关系及生命周期转换。

字段校验、旧序号过滤及后续状态校验的顺序遵循[校验与幂等](trading.md#校验与幂等)。旧柜台回报忽略后，不再进行历史成交冲突检查；新序号复用成交 ID 才由引擎的共享索引拒绝。跨订单身份唯一性、账户约束和全局容量检查也由引擎完成。

| 结果 | 语义 |
| --- | --- |
| 已应用 | 更新业务状态并返回动作；动作允许为空 |
| 已忽略 | 状态不变，不产生动作 |
| 错误 | 状态不变，不产生可执行动作，返回错误码及诊断 |

迟到受理属于已应用，会推进回报位置；即使没有动作，也必须提交核心状态。

本地完成事件不占用柜台回报序号，也不刷新最后柜台接收时间。执行器按请求键有界保存待处理的本地结果，引擎将结果消费与核心更新一并提交；重复结果按完成记录幂等处理，旧尝试的结果不得清除新尝试。

## 请求执行器

### 请求身份与状态

执行器跟踪一次请求的执行过程。新单请求以 `ClientOrderId` 关联，撤单请求以 `(ClientOrderId, CancelRequestId)` 关联。

| 状态 | 含义 |
| --- | --- |
| `Queued` | 尚未尝试调用适配器，可以确定地在本地取消发送 |
| `InFlight` | 发送尝试已提交，等待确定结果；不保证柜台已经收到 |
| `Completed` | 已取得该请求的确定结果，或者已确定在发送前结束 |
| `Uncertain` | 发送失败、响应超时或断线导致结果不确定 |

正常路径为 `Queued → InFlight → Completed`。发送前取消为 `Queued → Completed`；结果不确定时进入 `Uncertain`，只有有效响应可以使其完成，不能直接退回 `Queued` 重发。

`Completed` 表示请求结束，不表示订单终结。新单受理后，新单请求已经完成，订单可以长期处于 `Working`；后续成交仍提交给核心。首条有效事件为成交或其他确定的新单结果时，也结束新单请求，不等待额外受理通知。迟到或重复回报继续交由核心按回报规则判断，不因请求已完成而丢弃订单事件。

执行器使用预分配队列、请求表和本地结果队列。完成请求释放 in-flight 容量，保留幂等及未消费结果所需的完成记录。完成记录区分柜台结果和本地未发送结果，后者不能作为接受后续柜台回报的发送依据。完整订单和成交历史由核心及引擎持有。

### 输入与输出

| 输入 | 处理及输出 |
| --- | --- |
| 核心的 `SubmitOrder` 或 `CancelOrder` 命令 | 建立 `Queued` 请求，预留队列及跟踪容量 |
| 调度推进 | 按预算选中请求，准备 `InFlight` 变更及传输操作；提交后调用适配器 |
| 经验证的柜台回报 | 关联请求、准备其完成状态；订单业务事件继续交给核心 |
| 订单终态变化 | 检查是否存在尚未发送的撤单，必要时取消发送并安排本地结果 |
| 停止时取消未发送新单 | 移除 `Queued` 新单，安排新单发送前取消完成事件 |
| 适配器发送失败、响应期限到达或断线 | 将相关已尝试发送的请求标为 `Uncertain`，向引擎报告执行故障 |

执行器的输出包括请求状态和队列变化、提交后执行的适配器操作、交给核心的本地业务结果，以及交给引擎的执行故障。纯发送进度与诊断不传给核心。

回报关联检查不能先提交执行器状态。核心、共享索引或账户校验失败时，该回报引起的请求完成也必须丢弃。核心忽略旧回报时，执行器不重复完成请求或产生本地结果。

### 成交与撤单竞争

| 全部成交时的撤单请求 | 处理 |
| --- | --- |
| 不存在 | 订单保持 `Filled`，无需等待撤单 |
| `Queued` | 原子地移除发送安排，将请求结束并安排 `CancelNotSent` 本地结果；不调用柜台撤单 |
| `InFlight` | 保留该次请求，等待匹配结果，通常为无法撤销已成交订单的撤拒 |
| `Uncertain` | 保留不确定事实，等待有效响应，不能按未发送请求在本地结束 |

执行器在处理同笔已验证的全成事件时准备上述变更，随订单及账户一起提交。下一次发送调度不能再选中已取消发送的撤单。

本地结果按事件预算处理。结果尚未被核心消费时，核心可以保持 `Filled + cancel_pending`；本地结果队列必须参与排空判断。核心处理 `CancelNotSent` 后清除该次尝试并发布更新，客户端据此结束未决撤单。

### 发送失败、超时与停止

执行器在调用适配器前记录发送尝试并提交 `InFlight`。调用失败后请求进入 `Uncertain`，引擎报告错误及未确认订单，按错误路径退出。订单生命周期、未决撤单身份和资源预占保持原值，不自动重发或伪造拒单、撤单结果。

响应期限从发送尝试开始计时，时间由引擎注入，期限参数属于执行器或接入配置。心跳存活不能替代请求响应检查。当前 CTP 桥的新单确认和撤单等待复用 `--connect-timeout-seconds`，默认 60 秒；引入执行器时统一请求跟踪，适配器仍负责连接与原生协议错误。

整体停止期限仍由引擎管理，沿用 `shutdown_timeout_ns`，默认 5 秒，从开始停止计时。任一适用期限或连接故障可触发错误收尾；超时不能把 `Uncertain` 改为 `Completed`，也不能清除核心的未决尝试。

停止或断线后的持续撤单意图、自动重试许可和请求 ID 分配由引擎负责。工作中订单撤拒后，自动重试最早等待 10 ms，再通过新的本地撤单受理事件建立新尝试。普通手动撤单不自动重试，也不受该自动重试间隔阻挡。

## 事务提交与依赖

核心的应用入口为：

```cpp
OrderApplyResult Apply(const OrderEvent& event) noexcept;
```

事件包含确定时间，结果按值返回动作；输入只在调用期间借用。核心和执行器都准备候选变更，不在校验期间直接执行外部发送。

```text
处理本地请求、柜台回报或执行器本地结果
  → 在核心副本应用业务事件
  → 准备执行器变更、账户、索引和结果队列
  → 完成容量、关联和去重检查
  → 无失败提交核心、执行器、账户及索引
  → 执行适配器操作，或发布已提交通知
```

纯发送调度、超时及执行故障只更新执行器或引擎，不调用核心。队列、本地结果、成交记录及账户变更均须预留容量。正常提交路径中，校验失败时丢弃整个候选事务，不消耗请求身份；模拟期货保留原子账本操作边界，确保其成功后只剩不会失败的发布步骤。

宿主执行一次已提交的外部操作。通知投递失败由宿主单独处理，不重新应用原事件触发发送或记账。

| 组件 | 必需依赖及生命周期 |
| --- | --- |
| `OrderCore` | 模型类型、基础错误类型、标准库值类型；按值持有不可变规则，无运行时服务依赖 |
| `OrderRequestExecutor` | 请求及订单事件类型、调度配置、宿主注入的时间；输出传输计划，由引擎提交后调用适配器 |
| `TradingEngine` | 核心、执行器、适配器、账户及全局索引；协调所有权与提交顺序 |

全部组件由主线程串行驱动，无内部锁。适配器及其他借用依赖的生命周期覆盖执行器和引擎。事件、动作及跟踪数据自持，预分配完成后不进行动态申请、释放或扩容。

## 实时、回放与测试

核心不接收实时或回放模式标志。相同规则、初始状态及输入事件产生相同状态和动作。调用方提供事件及处理时间，并决定是否执行返回的外部动作。

| 场景 | 内部处理 | 外部操作 |
| --- | --- | --- |
| 实时 | 提交核心、请求、队列、账户和索引变化 | 提交后发送和通知 |
| 事件回放 | 按输入顺序应用相同事件 | 消费传输和通知动作，不实际发送或回调 |
| 单元测试 | 分别断言核心转换、执行器转换及集成提交结果 | 使用替身记录 |

本地结果的产生和消费分别处理：例如全成事件使执行器结束 `Queued` 撤单并安排结果，后续本地结果事件才清除核心的 `cancel_pending`。回放相同事件时，也必须保留这一先后关系。

## 实现归属与验证

核心和执行器作为 `yquant::trading` 库中的独立模块。

| 文件 | 内容 |
| --- | --- |
| `include/yquant/trading/order_core.h`、`src/trading/order_core.cc` | 业务状态机、事件及动作 |
| `include/yquant/trading/order_request_executor.h`、`src/trading/order_request_executor.cc` | 发送队列、in-flight 跟踪、本地结果及期限处理 |
| `tests/trading/order_core_test.cc` | 无调度器、适配器和账户服务的状态与动作测试 |
| `tests/trading/order_request_executor_test.cc` | 发送、关联、超时和竞争测试 |

相关枚举完整覆盖分支，构建启用 `-Werror=switch`。测试按业务预期独立表达状态、数量和动作，覆盖：

- 核心创建、受理、部分及全部成交、拒单、撤单结果和主动撤单。
- 首条成交隐含受理、迟到受理、回报序号幂等及非法转换。
- 相同核心事件不受请求排队时间、发送预算或执行器内部布局影响。
- 新单受理即结束请求，后续成交仍更新订单。
- 未发送新单在本地取消；全成时未发撤单产生 `CancelNotSent`，不调用适配器。
- 全成时已发撤单继续等待结果；本地结果不占柜台序号，并正常推进客户端报告流。
- 发送失败和超时保留 `Uncertain`，不自动重发或伪造业务结果。
- 正常路径的去重、容量或账户检查失败不提交部分状态；结果队列满时不丢失未决尝试。
- 预分配后的核心和执行器热路径无堆内存活动，排空同时覆盖订单、请求及待消费结果。
