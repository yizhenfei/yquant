# 订单核心状态机

`trading::OrderCore` 管理单笔订单的状态，接收事件并产生动作命令。相同初始状态、规则参数和事件序列产生相同的状态与命令序列，实时处理、日志回放和单元测试共用转换逻辑。

## 职责与边界

订单核心持有订单属性、生命周期、发送进度、撤单进度及已接受回报的位置。它校验单笔订单的事件并更新自身状态，由 `TradingEngine` 执行其输出的动作。

| 对象 | 职责 |
| --- | --- |
| `OrderCore` | 单笔订单的事件校验、状态转换和动作生成 |
| `TradingEngine` | 本地受理、全局调度、账户及索引处理、持久化与事务提交 |
| `TradingAdapter` | 请求发送和柜台回报归一化 |
| 策略侧交易服务 | 接收已提交的订单和账户视图，分发策略回调 |

核心不调用适配器、账户账本、时钟、日志或策略，不查询外部可变状态。权限、账户类型与标的适配、资源预占及全局容量检查由引擎完成。核心只接收经过这些检查的本地受理事件；订单与资源预占在同一事务中提交，本地受理失败不建立订单核心。

公共标识、计量和快照沿用[委托模型](trading.md#委托模型)。本文维护状态机的输入、输出及执行边界；回报字段和幂等业务规则集中维护在[柜台回报与委托账本](trading.md#柜台回报与委托账本)。

## 状态模型

### 生命周期

| 状态 | 含义 |
| --- | --- |
| `PendingNew` | 本地已受理，尚未确认柜台受理，包含待发送阶段 |
| `Working` | 柜台已受理或已有部分成交，仍有剩余数量 |
| `Filled` | 全部成交 |
| `Canceled` | 剩余数量已取消，已有成交保持有效 |
| `Rejected` | 柜台拒绝新单 |

部分成交通过数量字段表达，生命周期保持 `Working`。创建前的对象不提供有效订单快照；该初始化阶段不增加 `model::OrderState` 枚举项。

### 请求进度

生命周期、新单发送进度与当前撤单进度分别表达不同事实。

| 维度 | 状态 | 含义 |
| --- | --- | --- |
| 新单发送 | 待发送 | 已安排发送，尚未尝试调用适配器 |
| 新单发送 | 已尝试发送 | 已记录一次发送尝试，订单可能已到达柜台 |
| 新单发送 | 待处理本地取消 | 已阻止发送，等待本地取消事件处理 |
| 新单发送 | 本地取消完成 | 从未尝试发送，已完成本地取消 |
| 当前撤单 | 无未决撤单 | 没有需要继续发送或等待结果的撤单尝试 |
| 当前撤单 | 待发送 | 已登记撤单请求，尚未尝试调用适配器 |
| 当前撤单 | 已尝试发送 | 已记录该次发送尝试，等待对应结果 |

核心保留最近一次撤单请求 ID，结束该次尝试不清除其历史身份。`OrderSnapshot::cancel_pending` 由撤单进度派生，待发送和已尝试发送均为 `true`。

三个维度受以下约束：

- 新单待发送或待处理本地取消时，生命周期只能为 `PendingNew`。
- 本地取消完成后，订单状态为 `Canceled`，回报序号为零，且没有未决撤单请求。
- 已登记的撤单可以与 `Working` 或 `Filled` 并存。全部成交不撤销已经排队或发送的撤单尝试。
- 发送调用失败不回退到待发送，也不将订单认定为拒单。
- 订单全部成交后，仅在仍有未结束的撤单尝试时保留未决请求；没有未决撤单时无需等待撤单结果。网关整体排空还需检查全局队列及适配器。

### 持有的数据

核心保存原始委托属性、`ClientOrderId`、`AdapterOrderId`、累计成交量、剩余量、最近接受的回报序号和接收时间，以及请求进度。核心快照中的 `StrategyOrderId` 保持为零，由网关路由层补充策略身份。

价格步长、数量步长和柜台主动撤单许可作为不可变规则随订单建立。核心按值持有这些规则，不保留标的字典引用。

资源预占金额、冻结持仓、账户余额、全局索引、发送队列位置和自动撤单重试时刻保存在引擎中。

## 输入事件

所有运行期状态变化通过事件应用入口完成。事件带有确定的订单身份和处理时间；撤单相关事件还携带具体尝试 ID。规范化柜台回报使用 `model::TradingEvent` 载荷，本地控制事件使用独立的订单事件类型，不依赖 WAL 编码类型。

### 本地受理与执行

| 事件 | 前置条件 | 状态变化与动作 |
| --- | --- | --- |
| 本地订单受理 | 尚未建立订单；引擎已完成受理检查及资源预占准备 | 建立快照，进入 `PendingNew`、新单待发送；产生 `QueueNewOrder` |
| 执行新单发送 | 新单待发送，仍为 `PendingNew` | 标记已尝试发送；产生 `SendNewOrder` |
| 本地撤单受理 | `Working` 且无未决撤单；提供新的有效尝试 ID | 登记尝试，进入撤单待发送；产生 `QueueCancel` |
| 执行撤单发送 | 指定尝试仍待发送；生命周期为 `Working` 或 `Filled` | 标记该次尝试已尝试发送；产生 `SendCancel` |
| 请求取消未发送订单 | 新单待发送，尚未尝试发送 | 进入待处理本地取消；产生 `ScheduleLocalCancel` |
| 执行本地取消 | 正在等待本地取消处理 | 进入本地取消完成及 `Canceled`，剩余量归零；产生资源释放和 `CanceledBeforeSend` 订单通知 |
| 发送调用失败 | 对应新单或指定撤单已经尝试发送 | 保留订单及尝试状态；产生 `ReportSendFailure` |

“执行新单发送”和“执行撤单发送”表示本地调度器已经选中请求，要求推进一次发送尝试。它们不表示柜台受理，也不表示发送成功。引擎在记录并提交这次尝试后才调用适配器。

创建和撤单受理只安排发送。调度器负责全局公平性、发送额度及停止策略，并在取出对应请求时产生执行事件。停止时，对未发送新单产生本地取消事件，不产生新单发送事件。本地取消继续占用本地交易事件处理额度。

### 柜台回报

| 事件 | 状态变化 | 动作 |
| --- | --- | --- |
| 受理 | `PendingNew → Working`；保存首次获得的适配器订单 ID | 发布订单更新 |
| 迟到受理 | 保留已有的 `Working`、`Filled` 或 `Canceled`；推进回报序号和时间，必要时保存首次获得的 ID | 不重复发布订单更新 |
| 拒单 | 合法的待受理订单进入 `Rejected`，剩余量归零 | 释放剩余委托资源，发布订单更新 |
| 成交 | 更新累计量及剩余量，进入 `Working` 或 `Filled` | 应用本笔成交，发布订单更新 |
| 撤单成功 | 结束匹配尝试，进入 `Canceled`，剩余量归零 | 释放剩余委托资源，发布订单更新 |
| 撤单拒绝 | 结束匹配尝试，保留订单生命周期及剩余量 | 发布包含撤拒原因的订单更新 |
| 柜台主动撤单 | 规则允许且没有本地未决撤单时，待受理或工作中订单进入 `Canceled` | 释放剩余委托资源，发布订单更新 |

成交可以先于受理，直接使待受理订单进入 `Working` 或 `Filled`。迟到受理仍是受理回报，以上两行按当前状态区分处理，不新增柜台事件类型。

上述转换允许首条有效柜台事件就是成交，不要求所有接入都先提供独立受理通知。[FIX 订单状态规范](https://www.fixtrading.org/wp-content/uploads/download-manager-files/Order-State-Changes.pdf)的第 4 章包含首条回报直接为部分或全部成交的流程；具体接入的消息顺序由适配器按接口契约归一化。当前 CTP 桥在发布首笔成交前生成受理事件，因此其输出保证受理先于成交。

首次获得 `AdapterOrderId` 属于核心字段更新。受理、成交或柜台主动撤单等合法回报都可能首次提供该身份；保存身份与生命周期转换独立。核心不产生 `BindAdapterOrderId` 命令，引擎在提交时根据字段变化验证全局唯一性并建立索引。后续撤单命令携带已保存的 ID。

### 恢复控制

检查点通过受校验的初始化入口建立核心，不重新生成创建、记账或发送动作。恢复得到的待发送请求由“接管遗留请求”事件处理：

- 新单待发送转为已尝试发送；撤单待发送转为已尝试发送。
- 产生移除对应旧发送安排的动作，不产生 `SendNewOrder` 或 `SendCancel`。
- 生命周期、累计成交量和资源预占保持不变，等待恢复协调器完成核对。

接管事件表达恢复时对外部结果的不确定性，不伪造一次实时发送。待处理本地取消保留原有阶段，按恢复后的本地事件队列继续处理。对账恢复通过受校验的初始化入口安装订单和账户基线，历史成交不重新作用于账户。

## 动作命令

命令描述由宿主执行的操作，携带自持有界数据，不包含回调或组件指针。一个事件可以产生零个或多个命令，命令输出使用有界存储。

| 命令 | 载荷与执行语义 |
| --- | --- |
| `QueueNewOrder` | 订单身份；为后续发送安排一个新单请求 |
| `SendNewOrder` | 订单身份及原始请求；消费对应待发送项，提交尝试后调用适配器 |
| `QueueCancel` | 订单身份及撤单请求 ID；安排该次撤单发送 |
| `SendCancel` | 订单身份、适配器订单 ID 及撤单请求 ID；消费对应待发送项，提交尝试后调用适配器 |
| `ScheduleLocalCancel` | 订单身份；原子地移除新单发送安排并安排本地取消处理 |
| `RemoveRecoveredRequest` | 订单身份、请求种类及必要的撤单 ID；移除恢复遗留发送安排，不调用适配器 |
| `ApplyExecution` | 本笔成交及转换前后的订单信息；准备成交记录、账户记账和相应冻结资源消耗 |
| `ReleaseRemainingReservation` | 订单身份及终态原因；准备释放尚未被成交消耗的委托资源 |
| `PublishOrderUpdate` | 本次事件对应的订单快照、事件种类、撤单尝试 ID 及原因；提交后发布 |
| `ReportSendFailure` | 失败的发送种类、订单身份、必要的撤单 ID 及诊断；报告异常并交给宿主执行错误收尾 |

成交引起的资源消耗由 `ApplyExecution` 处理，全部成交不额外产生一次剩余资源释放。撤单拒绝不释放资源，也不产生新的撤单发送命令。

`ApplyExecution` 同时向通知层提供本笔成交。宿主完成提交后，按[落账与回调顺序](trading.md#落账与回调顺序)先发布订单更新，再发布成交。两个通知之间不处理下一条交易事件。

核心不产生 WAL 写入命令。每次有效状态变化由宿主统一记录，避免订单转换逻辑依赖持久化实现。

## 校验与应用结果

核心负责能够由单笔订单状态、规则参数和当前事件判定的校验：

- 订单及撤单尝试身份匹配，适配器订单身份保持一致。
- 事件字段、时间、价格和数量满足模型及委托约束。
- 回报序号连续，累计成交与本笔成交一致，状态转换合法。
- 发送和本地取消事件符合对应请求进度，同一次发送不会执行两次。

字段校验、旧序号过滤及后续状态校验的顺序遵循[校验与幂等](trading.md#校验与幂等)。旧序号不执行依赖当前状态的转换校验，不产生重复记账或通知。

引擎负责单笔快照无法判定的检查：跨订单 `AdapterOrderId` 唯一性、历史成交键 `(ClientOrderId, ExecutionId)` 是否重复、全局容量和账户约束。这些检查在接受候选状态前完成。核心判定为旧序号忽略的回报不再进行成交历史冲突检查；只有新序号成交才查询去重索引。历史成交存储保留在共享索引中，核心不主动查询历史组件。

| 应用结果 | 核心及动作语义 |
| --- | --- |
| 已应用 | 输入合法，按转换结果更新状态并返回动作；允许状态保持不变而仅产生诊断动作 |
| 已忽略 | 合法旧序号回报；状态保持不变，动作为空 |
| 错误 | 输入非法；状态保持不变，不产生可执行动作，返回错误码及诊断 |

迟到受理属于已应用，会推进回报位置，动作可以为空。调用方不能依据动作是否为空判断是否需要持久化。非法本地请求通过调用结果返回拒绝，不建立未决尝试；非法柜台回报由引擎进入错误收尾。

## 执行与事务提交

关键应用入口为：

```cpp
OrderApplyResult Apply(const OrderEvent& event) noexcept;
```

`OrderEvent` 自持事件载荷及处理时间，`OrderApplyResult` 按值返回结果和命令。输入只在调用期间借用。核心在输入非法时保持自身状态；调用者使用副本形成跨组件的候选事务。

```text
复制当前订单核心
  → 应用事件，获得候选核心和命令
  → 验证全局索引与容量，准备队列和账户变化
  → 写入对应日志事实
  → 提交核心、队列、账户和索引
  → 执行外部发送，或发布已提交通知
```

排队、资源和索引动作先准备，随核心状态一起提交；调度事件及本地取消事件对应的队列项也在该事务内消费。外部发送和通知只在提交后执行。任一提交前检查或 WAL 写入失败，丢弃整个候选事务，不消耗请求身份或更新对外视图。模拟期货账本保留原子操作边界，确保其修改成功后只剩不会失败的提交步骤。

外部发送调用失败发生在发送尝试提交之后，统一按发送结果不确定处理。宿主将失败作为新事件交回核心，核心产生 `ReportSendFailure`，保留以下状态：

| 失败的调用 | 保留的订单状态 |
| --- | --- |
| 新单发送 | 生命周期为 `PendingNew`，新单进度为已尝试发送，资源预占保持不变 |
| 撤单发送 | 保留 `Working` 或 `Filled`，该次撤单仍为已尝试发送，等待结果；不释放剩余委托资源 |

宿主收到失败诊断后停止正常请求处理，输出发送错误及未确认订单信息，并按错误路径退出。该请求不重新入队，也不通过本地取消或拒单结束。持久化恢复依据已记录的发送尝试保留不确定事实，再通过恢复对账确认柜台结果；流程见[独立柜台对账契约](tradingd-persistence.md#独立柜台对账契约)。发送失败事件本身只产生诊断，不增加订单业务状态，不要求新增一类持久化状态变化。

宿主只执行当前已提交事件的命令一次，不根据查询到的订单状态重新生成命令。通知投递失败由宿主单独处理，不能通过重新应用原事件再次执行发送或记账。发送尝试与日志记录的恢复边界见[写入与恢复边界](tradingd-persistence.md#写入与恢复边界)。

全部成交后，已发送撤单等待与该次尝试 ID 匹配的结果，通常为“已成交，无法撤单”的撤拒；结果只结束撤单尝试，订单保持 `Filled`。已经登记但尚未发送的撤单也按现有请求契约继续发送；它属于本地未决请求，尚未形成柜台在途请求。

撤单等待期限由宿主和适配器控制，核心不读取时钟或自行超时。当前通用引擎没有逐撤单响应期限；CTP 桥从实际提交撤单时计时，超时参数复用 `--connect-timeout-seconds`，默认为 60 秒。网关停止排空另有整体 `shutdown_timeout_ns`，默认为 5 秒，从开始停止时计时。任一适用期限到达或连接故障时，宿主报告未确认撤单并走错误退出路径；超时不清除未决尝试，也不改写 `Filled`。

停止排空、客户端断线和自动撤单策略保留在宿主。停止排空时，宿主在工作中订单撤拒后维护最早 10 ms 的自动重试时间，到期后分配新的撤单请求 ID 并产生本地撤单事件。普通手动撤单不因此自动重试，再次手动撤单也不受该间隔阻挡。排空生命周期见[正常停止](trading.md#正常停止)。

## 依赖与所有权

核心的接口和实现只依赖 `yquant::model`、基础错误类型及标准库值类型，不依赖运行时服务。

| 输入或规则 | 来源与持有方式 |
| --- | --- |
| 订单属性及订单 ID | 本地受理事件携带，核心复制保存 |
| 撤单请求 ID | 宿主分配，随本地撤单事件传入，提交成功后消耗 |
| 价格、数量步长和主动撤单许可 | 建立订单时传入，核心按值保存 |
| 当前处理时间 | 事件携带；实时使用事务时间，回放使用记录中的时间 |
| 柜台回报 | 适配器归一化后传入，核心不保留 SDK 数据引用 |

单个核心由引擎订单记录按值持有，可复制，无内部锁。所有应用和查询由所属主线程串行执行。创建、事件处理和命令生成不动态分配内存；核心不保存完整事件流或完整成交历史。

## 实时、回放与恢复

核心不接收实时或回放模式标志。两个模式向同一入口提供订单事件，宿主决定动作的执行范围。

| 场景 | 内部动作 | 外部发送和通知 |
| --- | --- | --- |
| 实时处理 | 准备并提交队列、账户及索引变化，记录事实 | 提交后执行 |
| 日志回放 | 从已记录事实重建核心、队列、账户及索引，不再次写 WAL | 消费动作但不调用适配器或通知策略 |
| 单元测试 | 检查候选状态和完整动作序列；集成测试验证事务效果 | 使用测试替身记录 |

已有持久化事实映射为核心事件：

| `TradingMutationKind` | 核心事件 |
| --- | --- |
| `kNewOrder` | 本地订单受理 |
| `kCancel` | 本地撤单受理 |
| `kSendNew` | 执行新单发送 |
| `kSendCancel` | 执行撤单发送 |
| `kScheduleLocalCancel` | 请求取消未发送订单 |
| `kLocalCancel` | 执行本地取消 |
| `kReport` | 柜台回报 |

引擎仍验证全局 revision、请求队列顺序和编号分配；回放不绕过核心直接修改发送或撤单进度。恢复接管是历史回放之后的独立恢复控制事件，不解释为原历史中发生过发送；其结果经验证后纳入新的恢复基线和检查点。若将恢复控制事件加入逐条 WAL，须定义新的编码及旧日志读取策略，不能复用已有发送事实的数值。

检查点保存快照和内部请求进度，并保存重建核心规则所需的稳定标的定义。装载时，订单自身不变量由核心验证；账户、队列、历史成交及索引之间的一致性由引擎验证。调整内存字段归属不改变既有字段编码；既有尝试标志与新进度之间采用可逆映射，缺少或改变语义的新增持久字段按版本迁移处理。

生产持久化的账户范围继续遵循[交易网关持久化与恢复](tradingd-persistence.md)。核心转换逻辑对实时和回放共用，不扩展期货账本的持久化支持范围。

## 实现归属与验证

订单核心作为 `yquant::trading` 库中的独立模块：

| 文件 | 内容 |
| --- | --- |
| `include/yquant/trading/order_core.h` | 状态机、订单事件、应用结果和动作的公共接口 |
| `src/trading/order_core.cc` | 订单校验、状态转换和动作生成 |
| `tests/trading/order_core_test.cc` | 无柜台、无账户服务的状态与动作测试 |

新增状态、事件或动作时，相关枚举分支完整覆盖，构建启用 `-Werror=switch`。核心测试按业务预期独立表达数量、状态和动作，避免由实现规则生成预期值。

验证覆盖以下场景：

- 创建、排队、发送和受理；发送前取消不会产生柜台发送。
- 首次部分或全部成交先于受理；迟到受理推进回报位置而不重复通知。
- 部分成交后撤单成功，累计成交保持，剩余资源只释放一次。
- 撤单待发送或已发送时全部成交，保留尝试并处理其后续结果。
- 撤拒结束当前尝试；旧回报不能清除新尝试；自动重试受宿主策略控制。
- 允许和不允许柜台主动撤单的两类规则。
- 旧序号幂等、新序号缺口、身份变化、超量成交、非法转换和时间校验。
- 发送失败与恢复接管保留不确定状态，不自动重发。
- 同一事件序列在实时和回放中产生相同核心状态及命令；在每个切点通过检查点恢复后，后缀结果仍一致。
- 宿主历史成交去重、跨订单身份冲突、容量不足、账户处理或 WAL 失败均不提交候选状态和动作。
- 核心处理无堆内存活动，已有引擎和恢复集成测试继续验证账户、索引及排空语义。
