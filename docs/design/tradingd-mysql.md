# 交易历史 MySQL 存储

MySQL 保存交易历史及查询投影，网关继续通过本地检查点和 WAL 恢复。后台入库由可选构建项 `YQUANT_WITH_MYSQL` 启用，运行配置使用 `mysql_archive`。

## 职责与数据流

数据库采用 MySQL 8.4、InnoDB。入库工作由 `tradingd` 内独立后台线程执行，每个账本只有一个入库者；数据库连接、批缓冲及解析状态由该线程独占。交易线程不执行 SQL，不等待数据库连接或提交。

```text
交易线程：校验 → 追加 WAL → 应用内存账本 → 发送柜台或通知策略
同步线程：同步 WAL → 推进 durable_lsn
入库线程：读取可归档前缀 → 解码 → MySQL 事务提交
查询服务：读取 MySQL 投影及其消费水位
```

本地写入和故障恢复遵循[交易网关持久化与恢复](tradingd-persistence.md)。数据库不可用时保留本地待消费文件并重试，不改变逐笔受理语义。数据库中的资金、持仓用于查询，交易风控读取网关内存账本。

仅配置本地持久化时允许启用入库。数据库备份不能代替状态目录备份；增加异步入库不改变本地 WAL 的断电丢失边界。

## 归档来源与运行衔接

### 可消费前缀

入库必须同时满足记录已经应用于业务状态、对应 WAL 前缀已完成本地同步。交易线程在完整服务轮次结束后发布 `applied_lsn`，覆盖此前全部已应用记录；入库上限为同一运行的 `min(applied_lsn, durable_lsn)`。不能直接以 `published_lsn` 作为查询可见边界。

入库线程使用独立只读文件描述符和固定批缓冲读取段，不保留交易线程或映射段中的借用地址。新增支持活动日志的只读扫描器，校验格式、CRC、LSN 连续性和封口，不与现有 `Journal::ReplayFrom` 并发共享可变状态。扫描器到达消费上限即停止；上限内缺段、损坏或未知版本阻塞该账本归档，不跳过记录。

每条 WAL 原始记录均进入事件表，包括账本变更、模拟柜台事件和本地拒单。模拟柜台成交与账本应用可能分别记一条记录：成交查询投影以账本接受的成交为准，模拟事件只作来源证据，避免计算两次。

### 运行清单和账户基线

每次初始化或重启创建新 `run_id`，先保存不可变的归档运行清单及恢复基线，再开放交易。清单引用具体基线文件，包含账本身份、运行号、前驱运行号、前驱有效末游标、覆盖状态和格式版本。基线文件不得依赖以后会被改写的 `CURRENT`；文件及目录同步成功后才发布清单。

基线保存恢复完成后的资金、持仓、订单及成交去重状态，另附持久客户归属和完整标的字典。重启时撤销旧模拟订单、结清回报等变化发生在新日志流开始前，由新运行基线表达；历史查询可显示为恢复边界，不补造逐笔回报时间。

运行中新登记的客户端在发送 `Welcome` 前，随身份冷路径保存以身份命名域编号命名的不可变 `IDENTITY` 副本。后台读取最新副本，只允许新增会话，核验已有归属和字典不变。归档记录中的槽号转换为稳定会话 ID；引用新会话的事件与会话元数据在同一事务提交。后台不读取正在修改的内存身份表。

入库按前驱关系处理运行：先消费前驱有效前缀，再安装新基线，然后消费新流的 LSN 1 及后续记录。`run_id` 与其他命名域共享分配器，不能要求运行号连续。正常关闭同步最终 WAL 后写入结束清单；异常退出由下一次恢复确定旧流有效边界并耐久保存。清单发布过程可重复，不能改写已经归档的事实。

快照可能覆盖断电后没有存活的 WAL，基线能够恢复状态，却无法恢复全部逐笔历史。此时保存历史缺口及边界，不生成虚假的事件。数据库已归档水位若超出恢复认定的旧流有效边界，停止归档并报告冲突，保留原数据供核查。

对已有状态首次启用入库，以当前恢复基线作为查询起点，标记更早历史未覆盖。更早保留文件的导入须单独验证字典、身份及运行衔接，不自动宣称全历史完整。

## 表结构

### 公共字段和编码

- 所有表使用 InnoDB。`ledger_id` 使用 `BINARY(16)`，按两个 64 位身份字段的固定大端顺序编码，不复制 C++ 内存布局。
- `run_id`、LSN、会话、订单、撤单、修订号及标的 ID 使用 `BIGINT UNSIGNED`，保持 C++ 无符号 64 位值域。MySQL 的整数范围见[官方文档](https://dev.mysql.com/doc/refman/8.4/en/integer-types.html)。
- 金额、价格和数量使用有符号 `BIGINT`，保存账本原始整数单位；单位由对应运行的标的字典及账务版本解释，不使用浮点数重新计算账本。
- 柜台委托号、执行号及命名域使用 `VARBINARY` 按字节比较。委托号与执行号的容量沿用适配器契约，当前外部标识上限为 64 字节；其他字段各自校验长度，禁止截断。
- 原始单调时间使用 `BIGINT UNSIGNED`，只在所属运行内解释。柜台业务时间保存来源给出的精度、时区及交易日；缺失时为 NULL，不用入库时间替代。`ingested_at` 使用 UTC `DATETIME(6)`，只表示入库时间。
- 所有事实字段默认非空，允许缺失的来源字段显式可空；状态码及载荷版本使用明确的整数编码。DDL 迁移独立执行，运行线程只校验版本。

### 事实与元数据

| 表 | 主键或唯一键 | 主要字段与用途 |
| --- | --- | --- |
| `archive_schema` | 主键 `version` | 迁移版本、校验摘要、执行时间 |
| `ledgers` | 主键 `ledger_id` | 规范编码的 `account_key`、账务版本；身份绑定后不可修改 |
| `archive_runs` | 主键 `(ledger_id, run_id)` | 前驱运行、前驱有效末 LSN、基线版本及原始镜像、字典、客户归属、历史覆盖状态、可空的最终 LSN |
| `strategy_sessions` | 主键 `(ledger_id, strategy_session_id)`；唯一键 `(ledger_id, client_id)` | 持久客户 ID、归属、标的范围、规范编码的原始元数据；会话身份不可修改 |
| `trade_events` | 主键 `(ledger_id, run_id, lsn)` | 记录类型、编码版本、原始载荷 `BLOB`、原始单调时间、入库时间 |
| `archive_gaps` | 主键 `(ledger_id, run_id, gap_no)` | 缺口原因、已知边界、是否有状态基线；未知丢失范围保留 NULL |
| `archive_progress` | 主键 `ledger_id` | 当前运行、已安装基线标志、连续已提交 LSN、段号及偏移、投影版本、更新时间 |

`archive_runs` 的原始基线使用 `LONGBLOB`，归档基线整体受 64 MiB 上限约束，通过预处理参数绑定并在一个事务内发布；客户端和服务端包长度限制须容纳最大合法基线及协议开销。运行结束信息只能从未结束转为已结束，已经确定的前驱、基线及最终边界不得被不同内容覆盖。缺口编号由归档清单确定，重试不得重新编号。

`account_key` 作为身份元数据逐字节比较；同一账户可以因显式新建账本而具有不同 `ledger_id`，查询必须选择账本，不能自动合并。

### 查询投影

投影在事件或基线入库的同一事务内更新；订单和账户保存最后来源 `(run_id, lsn)`，成交保留首次来源。基线来源为新运行 LSN 0。

| 表 | 主键或唯一键 | 主要字段与用途 |
| --- | --- | --- |
| `orders` | 主键 `(ledger_id, strategy_session_id, local_order_id)`；唯一键 `(ledger_id, core_order_id)` | 标的、方向、价格、数量、累计成交、状态、柜台命名域及委托号、当前运行、最后来源；保存所有已知订单，包括本地拒单 |
| `fills` | 主键 `(ledger_id, execution_namespace, execution_id)` | 订单业务键、标的、成交价量、业务时间、首次来源、基线发现标志 |
| `order_updates` | 主键 `(ledger_id, run_id, lsn)` | 订单业务键、更新类型、状态、原因、累计成交；每条账本记录至多生成一行订单更新 |
| `account_cash` | 主键 `ledger_id` | 余额、可用、预占、最后来源 |
| `account_positions` | 主键 `(ledger_id, instrument_id)` | 总持仓、可卖、预占、不可卖部分、最后来源 |

本地拒单没有核心订单号时，`core_order_id` 为 NULL。会话、订单、柜台标识及成交命名域规则统一见[持久身份与状态](tradingd-persistence.md#持久身份与状态)。成交命名域必须按其业务字段规范编码，不能拼接有歧义的字符串或用散列替代原键。

基线原子替换资金、持仓投影，并按业务键合并恢复后的订单状态。基线中的历史成交按执行键核验或补入 `fills`，不再扣减余额与持仓；只有去重标识、没有完整成交字段时不补造明细，并标记明细覆盖不足。基线中缺少的旧订单保留历史，不能仅因缺席而改判终态。订单、成交引用的字典和归属信息从其来源运行解析，避免跨运行解释变化。

初始二级索引为 `orders(ledger_id, strategy_session_id, status)`、`orders(ledger_id, instrument_id, core_order_id)`、`fills(ledger_id, strategy_session_id, local_order_id)`、`fills(ledger_id, instrument_id, business_time)` 和 `order_updates(ledger_id, strategy_session_id, local_order_id, run_id, lsn)`。业务时间范围查询同时指定其时区与时间精度约定。事件表先使用主键顺序扫描，不预先增加时间分区。

## 入库事务与幂等

每账本串行处理，批次不跨运行；按记录数和载荷字节数双重限制批缓冲。默认上限为 256 条、1 MiB。每批条数按 `min(batch_records, batch_bytes / 最大载荷)` 保守限定，确保最坏载荷也不超过字节预算；有积压时连续提交，空闲时默认每 100 ms 检查水位。轮询周期不含数据库故障或网络等待。单条记录上限沿用 WAL 约束。

```text
读取并校验连续批次，边界不超过可消费前缀
BEGIN
  SELECT archive_progress ... FOR UPDATE
  核验运行、起始游标和投影版本
  逐条插入或核验 trade_events
  仅对新事件更新订单、成交、资金及持仓投影
  将 archive_progress 更新为整批末游标
COMMIT
```

首次创建进度行使用唯一主键处理竞争，再重新加锁读取。批次起点必须等于数据库进度的下一位置；不一致时重新读取进度和本地源，不能强行覆盖。不同入库者即使意外指向同一账本，也只能在锁内按该规则推进。

同一事件键和相同规范载荷表示重复消费；类型、版本或载荷任一不同均回滚并停止该账本归档。规范载荷逐字节比较，CRC 只用于检测文件损坏。相同成交执行键同样核验业务内容，来源事件可以不同，不得重复计入成交。

不使用 `INSERT IGNORE` 吞掉约束错误，不用无条件 UPSERT 改写事实。MySQL 的 [`ON DUPLICATE KEY UPDATE`](https://dev.mysql.com/doc/refman/8.4/en/insert-on-duplicate.html) 会对唯一键冲突执行更新；事实表使用普通 INSERT，对重复键错误显式查询和核验。

COMMIT 返回成功后才推进内存消费游标。连接在提交阶段断开时，结果视为未知；重连后从数据库进度重读，允许再次处理同一批。死锁、锁超时等可重试错误先回滚整批，有限退避后重试；字段溢出、内容冲突和版本不兼容保留诊断并停止归档。

运行基线、缺口和进度 LSN 0 在同一事务内安装。大基线事务在后台执行，不拆成查询可见的部分状态。订单按本批变更写入，资金和持仓使用后台影子账本的完整状态更新。在线投影重建工具尚未提供；维护重建须使用独立目标及进度，核验后切换。

## 查询一致性与历史覆盖

资金、持仓、订单及进度的联合查询使用 `REPEATABLE READ` 的只读一致性快照事务，返回 `(ledger_id, run_id, archived_lsn)` 及历史覆盖状态；`archived_lsn` 是数据库已提交的消费水位。需要指定订单之后的视图时，等待消费水位覆盖该订单的来源事件，并设置超时，不以入库时间判断。

跨运行排序沿运行前驱关系，再按 LSN 排序；不能将单调时钟或柜台业务时间作为日志连续性依据。恢复基线提供状态连续性，历史缺口仍在查询中保留。数据库无法仅凭新基线证明全部历史明细完整。

## 配置、运行与保留

入库配置单独命名为 `mysql_archive`，包含启用开关、主机、端口、库名、用户、密码环境变量名、TLS CA 路径、连接与读写超时、批次上限和重试退避。密码不写入日志；远程连接校验服务器证书和主机名。预处理语句绑定业务字段，库表名由固定实现定义。

数据库需采用严格 SQL 模式，拒绝字段截断及越界转换。部署使用 `innodb_flush_log_at_trx_commit=1`；启用 binlog 时使用 `sync_binlog=1`，并验证实际存储同步能力。相关耐久设置见 [InnoDB 与 ACID](https://dev.mysql.com/doc/refman/8.4/en/mysql-acid.html)。副本切换是否可能丢失已确认提交须由部署明确，不将普通异步复制视为零丢失保证。

启用入库后，数据库暂时不可达不阻止网关恢复和交易；配置语法错误在启动校验时报错。连接成功后再校验数据库版本与表结构，错误只阻塞归档并告警。正常退出完成本地最终同步与检查点，写本地结束清单；后台追平后在事务内设置当前运行 `final_lsn`。`shutdown_ms` 限制继续发起 SQL 的期限，已进行的单次网络调用仍受连接或读写超时约束，线程加入后才释放本地文件。未追平时保留积压并报告。

数据库通过 `archive_progress`、`archive_runs` 和 `archive_gaps` 提供消费水位、更新时间、结束及历史覆盖信息；后台故障日志带运行号和已消费 LSN。工作线程每 100 ms 检查磁盘空间，数据库故障期间仍检查。待消费字节数及最老积压时间的指标导出尚未提供。磁盘触及部署保留阈值时停止新单，继续按网关故障规则处理回报及必要撤单，不能为腾空间删除未归档数据。

自动清理暂不实现。后续清理同时要求恢复检查点不再依赖目标文件、数据库已归档、运行基线仍可解释历史，且满足独立备份保留要求。数据库恢复到较旧备份时，从其进度重新消费本地文件；源文件已被清理则停止并报告缺口，不伪造完成水位。

## 构建与部署

安装 Oracle MySQL 客户端开发库后，在原有构建命令中启用：

```sh
cmake --preset debug -DYQUANT_WITH_MYSQL=ON
cmake --build --preset debug
```

非标准安装目录可指定 `YQUANT_MYSQL_INCLUDE_DIR` 和 `YQUANT_MYSQL_LIBRARY`。未启用时不依赖客户端库，配置开启归档会在启动校验时报错。运行时要求 MySQL 8.4 或以上，且上述耐久设置满足要求。

先创建数据库与账号，再由迁移账号在目标库执行 [trading_archive_v1.sql](../../sql/trading_archive_v1.sql)。工作线程不执行 DDL，校验迁移版本及表引擎。归档账号仅授予这 12 张表所需的 SELECT、INSERT、UPDATE、DELETE；迁移版本表只需 SELECT。数据库备份覆盖全部归档表。

配置示例为 [mysql.json](../../examples/tradingd/mysql.json)。通过环境变量提供密码，首次初始化和后续启动遵循本地持久化规则：

```sh
export YQUANT_MYSQL_PASSWORD='your-password'
./build/debug/bin/yquant-tradingd --config ./build/debug/tradingd/mysql.json --initialize-state
./build/debug/bin/yquant-tradingd --config ./build/debug/tradingd/mysql.json
```

远程主机必须提供 `tls_ca`，路径相对网关配置文件解析，并启用证书及主机名校验。配置中的时间与容量边界为：连接及单次读写超时 1–30 秒；批次 1–4096 条、16 KiB–16 MiB；轮询及退避 1–60000 ms；关闭追平期限 0–60000 ms。默认磁盘保留量为 64 MiB，应按实际写入速度和退出所需空间提高。

本地归档文件使用 `archive-base-<run>.bin`、`archive-run-<run>.bin`、`archive-end-<run>.bin` 和 `archive-identity-<namespace>.bin`。基线封装身份、字典与网关检查点，不含连接令牌和数据库密码；清单发布前不开放监听。

真实数据库测试先在独立测试库安装同一迁移，再设置 `YQUANT_MYSQL_TEST_DATABASE`、`YQUANT_MYSQL_TEST_HOST`、`YQUANT_MYSQL_TEST_PORT`、`YQUANT_MYSQL_TEST_USER`、`YQUANT_MYSQL_TEST_PASSWORD` 后运行测试。未设置数据库名时跳过数据库集成用例；普通日志及投影测试不依赖数据库。

## 实现与验收

实现由 `mysql_archive` 工作线程、`archive_projection` 影子账本和 `mysql_archive_store` 数据库事务层组成。只读扫描器与原有恢复共用日志格式校验，独立文件描述符保证不共享 `Journal` 可变状态。数据库客户端使用 MySQL C API，错误通过显式返回值处理。

验收要求：

- 订单、拒单、撤单、部分成交和终态成交的字段及来源准确，模拟事件不重复生成成交。
- 已发布但未应用或未同步的记录不入库；活动段读取与轮转并发时无缺口或悬空引用。
- 批次提交前崩溃整体回滚，提交成功但响应丢失后重试不重复记账；数据和进度始终一致。
- 同键同内容可重试，同键异内容停止归档；越界、截断及未知版本不被忽略。
- 重启结清模拟订单后，新基线正确衔接；历史缺口、首次启用和基线覆盖丢失 WAL 的情况可查询。
- 运行中新登记的客户可还原稳定归属，会话元数据先于引用事件可见，重复导入内容一致。
- 两个入库者竞争进度不重复应用投影；账户之间独立推进，单账本冲突不阻塞其他账本。
- 数据库断连、重启、死锁及长事务期间交易线程不等待 SQL，积压有界使用内存且重连后可追平。
- 查询同一快照内资金、持仓和消费水位一致；从备份重放及投影重建得到相同结果。
- 对比启用前后的交易路径分位延迟、归档吞吐、积压恢复速度及内存上界。

数据库事务和故障测试使用真实 MySQL 8.4 实例，客户端替身只覆盖错误分支；不能用替身测试替代提交结果未知等集成验收。
