# 系统架构

项目定位与首版范围见 [README](../../README.md)。

## 总体架构

YQuant 通过 service 实现不同的业务功能。service 可以灵活组装到同一个进程或不同进程中，也可以部署到不同机器上。

### 业务服务

| service 类型 | 职责 |
| --- | --- |
| `market-service` | 接收行情，按订阅向策略分发。 |
| `strategy-service` | 承载一个或多个策略实例，使用行情和交易回报生成交易指令。 |
| `trade-service` | 接入交易接口，处理报单、撤单和回报，维护订单及成交状态。 |

service 类型定义功能，service 实例是部署单位。同一种 service 可以创建多个实例，并分别组装到不同程序中。

多个策略可以通过交易服务共用同一个交易账户，订单及成交回报需要正确分发给对应策略。

### 部署方式

| 部署方式 | 使用的程序 | 组装示例 |
| --- | --- | --- |
| 单进程部署 | `monod` | 将行情、策略和交易 service 组装在同一个进程中。 |
| 单机多进程部署 | `marketd`、`strategyd`、`tradingd` | 在同一台机器上分别运行行情、策略和交易进程，可以启动多个 `strategyd` 分别承载策略 service 实例。 |
| 多机部署 | `marketd`、`strategyd`、`tradingd`、`relayd` | 将业务进程分布到不同机器上，在各参与跨机通信的机器上增加 `relayd` 负责转发。 |

单进程部署通过直接调用降低通信开销；多进程部署获得并行处理能力和进程隔离。同进程中的 service 共享故障边界。多个策略 service 实例可以共用一个进程，也可以分别部署到独立进程。

### 部署拓扑

拓扑描述 host、进程和 service 实例之间的归属关系：

| 对象 | 标识及信息 |
| --- | --- |
| host | 具有唯一字符串 ID 和可互通的 IP 地址。 |
| 进程 | 具有进程实例 ID，归属于一个 host。 |
| service 实例 | 具有全局唯一的 service ID，归属于一个进程。 |

进程实例 ID 用于标识部署中的进程，不依赖操作系统分配的 PID。拓扑还指定各 host 的本地 relay-service，以及建立跨机连接所需的地址。

拓扑通过静态配置文件提供给各进程，用于选择调用实现和确定消息路由。配置的自动分发、拓扑的动态管理及专门的运维工具服务不纳入首版。

## 服务调用

两个 service 位于同一进程时，调用应保留直接函数调用的效率，避免为通信进行消息序列化、队列读写和数据复制；跨进程时使用消息通信。调用方通过统一接口使用服务，无需判断目标的部署位置。

### 调用契约

service 调用均通过 service client 进行，分为两类：

| 调用类别 | 返回与结果语义 |
| --- | --- |
| 请求类 | 调用返回表示请求已发出，实际执行结果通过对应回调获知。 |
| 缓存类 | 一般在返回时告知缓存是否可用；可用时可以立即获取结果。 |

请求与回报的关联方式由具体业务接口定义。例如，下单请求通过调用方的订单标识关联回报。

### service client

每种 service 定义相应的 service client 抽象接口，并提供处理响应和事件的回调接口。调用方依赖该抽象接口，通过多态选择具体调用路径：

| client 实现 | 调用路径 |
| --- | --- |
| 进程内 client | 直接调用本进程中的 service 对象。 |
| 跨进程 client | 将调用编码为消息，发给目标 service，并将返回消息转换为回调或缓存更新。 |

service client factory 根据目标 service ID 和拓扑判断目标是否属于本进程。对于本进程中的目标，从对应类型的本地实例表取得具体服务指针，创建进程内 client；对于其他进程中的目标，创建通过 message bus 通信的跨进程 client。使用方在初始化时通过 factory 获取 client，后续通过该接口调用服务。

接口可以使用 C++ 纯虚类表达。两种实现遵循上述调用契约，调用方不依赖某一种部署方式的执行细节。参数生命周期、具体回调时机及各接口的数据语义在接口设计中细化。

### service server

目标进程通过 service server 接收消息、反序列化请求并调用 service 接口，再将响应或事件序列化后返回。service 的业务实现无需判断调用是否来自远端。

client 与 server 的接口和消息格式需要配套维护；是否使用 IDL 及代码生成，在接口设计中确定。

### 查询与缓存

缓存是 service client 的功能之一。缓存类调用采用同步查询接口：进程内 client 可以直接查询 service；跨进程 client 维护本地状态缓存，通过响应和事件更新缓存，查询时读取本地缓存，不等待网络往返。

策略等使用方无需因部署方式不同而自行维护一套远端服务缓存。远端缓存反映已接收到的状态，可能落后于服务端。缓存初始化、数据一致性以及断连后的可用性判定在接口设计中细化。

### 重入处理

进程内直接调用可能形成调用环，响应或事件回调也可能在原调用返回前进入调用方。client 需要结合具体接口分析重入风险，并落实接口约定的回调时机。

需要打断调用环时，client 可以缓存请求或回调，交由后续运行周期处理。无需延迟的调用保留直接调用路径。延迟执行时，需要明确参数及结果的有效期和数据保存责任。

### 调用示例

以下以策略下单和查询订单状态为例，说明各组件如何协作。

#### 同进程下单

`monod` 同时承载策略和交易 service：

1. 初始化时，策略侧使用目标交易 service 的 ID 向 factory 获取 client。factory 根据拓扑创建进程内 client，连接本进程中的交易 service。
2. 策略侧生成调用方订单标识，通过 client 提交下单请求。client 直接调用交易 service，由交易 service 向柜台提交委托。
3. 交易 service 收到订单或成交回报后，经 client 的回调接口交付给策略侧，由策略侧关联到对应策略实例。

业务调用路径为：策略 → client → 交易 service。同进程的 client 与 service 之间无需进行消息编码和传输。

#### 跨进程下单

`strategyd` 和 `tradingd` 分别承载策略和交易 service：

1. 初始化时，factory 根据目标交易 service 的 ID 和拓扑创建跨进程 client。
2. 策略侧通过相同的 client 接口提交下单请求。client 将请求编码为消息，经两端 message bus 发送给交易进程中的 server。
3. server 将消息解码为接口调用，交给交易 service，由交易 service 向柜台提交委托。
4. 交易 service 收到回报后，由 server 编码并通过 message bus 返回。策略进程中的 client 解码回报，经回调接口交付给策略侧，再关联到对应策略实例。

业务调用路径为：策略 → client → 两端 message bus → server → 交易 service。两个进程部署到不同机器时，message bus 通过 relay 转发消息，策略仍使用相同的 client 接口。

在这两种部署中，调用方都通过自己的订单标识关联请求与回报。交易服务和柜台还具有各自的订单标识，由交易服务维护关联；具体字段、唯一性范围、生成规则和映射结构在交易接口设计中细化。service ID 用于定位服务，同一策略 service 内的策略归属也在该接口设计中明确。

#### 订单状态查询

策略通过 client 的缓存类接口查询订单状态，接口同步告知数据是否可用，可用时立即获取结果：

| 部署方式 | 查询路径 |
| --- | --- |
| 同进程 | client 直接查询交易 service 中的订单状态。 |
| 跨进程 | client 查询本地订单状态缓存，缓存通过收到的回报更新，查询本身不发送远端请求。 |

## 跨进程通信

message bus 以 service ID 为目标寻址，屏蔽同机与跨机传输的差异。请求消息由 service server 适配为接口调用，响应及事件由 client 处理。业务组件无需自行选择传输通道。

### 同机点对点通信

同一 host 上需要通信的进程对之间，建立基于共享内存的 SPSC 队列，每个方向使用独立队列。两个进程中的多个 service 复用进程间通道，由目标 service ID 区分消息接收方。通道的读写由各进程的业务线程负责，保持单生产者、单消费者约束。

### 单机广播

点对点通道逐个发送会重复写入同一份广播数据。具有广播需求的 service 可以配置共享内存 SPMC 队列，由该 service 的业务线程作为单生产者，供本机多个消费者读取，适用于行情向多个策略分发等场景。

广播与指定多个接收方的多播分别设计。首版只支持单机广播，不包含跨机广播；广播订阅方式及慢消费者处理规则在通信设计中细化。

### 跨机点对点通信

每个参与跨机通信的 host 运行一个 `relayd`，承载 relay-service。message bus 根据目标所在 host，选择本机通道或本地 relay。各 relay 持有全局路由信息，跨机消息按以下路径转发：

1. 发送端 message bus 通过本机共享内存通道，将消息交给本机 relay。
2. 本机 relay 根据路由信息，通过 TCP 将消息发送到目标 host 的 relay。
3. 目标 host 的 relay 通过本机共享内存通道，将消息交给目标进程的 message bus。

转发过程中保留原始源 service 和目标 service 的标识。返回消息按目标 service 的位置路由。

relay 转发会增加处理环节和延迟，相关优化在后续设计中展开。

## 执行与调度

### 单业务线程

YQuant 默认采用单线程设计。每个进程使用单个业务线程执行 service 和通信组件，组件的调用与状态访问在该线程内完成，通过多进程获得并行处理能力。处理函数需要及时返回，避免阻塞同一进程中的其他组件。

接入库可以具有内部线程。外部线程产生的事件交给业务线程处理，不在外部回调线程中直接执行 service 业务逻辑。

### 策略部署与隔离

同一个 `strategy-service` 中的策略实例共享业务线程，较慢的策略会影响其他策略的响应延迟。一个策略实例崩溃会导致整个进程崩溃，影响该进程中的所有 service。

适合共同部署的策略应具有较强相关性，并能接受彼此的延迟影响及共同承担进程故障。需要独立延迟与故障边界的策略，部署到不同进程。

### 循环调度

container 通过 `Service` 接口管理需要在主循环中持续运行的服务。主循环按注册顺序反复调用 `void Run()`，每次调用处理当前可用的工作并及时返回。已注册的服务持续参与调度，循环退出后统一解除注册。

需要持续处理事务的 client、message bus、server 和 relay 等组件，通过该接口参与运行循环，处理接收消息、缓存更新和延迟执行的调用。client factory 创建需要参与调度的 client 时，将其接入 container 的调度机制。注册关系覆盖组件的使用期，组件销毁前解除注册；每次调用的处理量在对应组件设计中细化。

程序组装层负责运行生命周期，向 container 提供退出条件，由运行循环检查并决定何时结束。业务组件通过状态或回调报告需要停止的情况，由运行控制层决定停止范围。

## 程序组装与依赖

container 作为统一的容器框架，以共享库的形式供各程序复用，承载 service 实例及通信组件的执行。`monod`、`marketd`、`strategyd`、`tradingd` 和 `relayd` 各自具有 `.cc` 组装代码，在 `main` 中选择具体实现、建立依赖关系并启动程序。

程序组装层建立本进程的 service 实例、拓扑访问、message bus、service server 和 client factory，并将所需接口注入使用方。本地实例表按 service 类型分别维护，保存对应具体类型的指针；组装层建立注册关系，向各 factory 注入对应实例表和部署信息，factory 负责选择并创建 client。取得本地实例时保留具体类型，无需下转型。

依赖倒置所需的具体实现绑定由程序组装层完成。例如，交易 service 依赖交易接口抽象，由组装代码创建 SimNow 接入实现并注入。

行情 service 依赖行情接入抽象，具体接入对象由程序组装层创建并注入。行情接收、缓冲复用和订阅分发在 service 内完成，由 container 调度该 service 推进接收流程。

container 不承担业务实例寻址，不依赖具体业务 service，也不负责选择业务实现。service 不依赖特定传输实现；client 和 server 承担业务接口与消息通信之间的适配。

共享实现放在所属库中，程序目录只保存该程序专用的组装及实现代码；共享库不依赖程序私有代码，程序之间不复用彼此的私有实现。
