# Trading 设计草案

Trading 提供订单处理与账户状态查询能力。一个 `TradingService` 管理多个账户，每个请求指定账户；多个策略可以通过同一账户交易。

线程与部署模型遵循[系统架构](architecture.md)。本设计覆盖 N2 的本地交易路径，并定义模拟场所、SimNow 接入及跨进程调用的扩展位置。

## 类与职责

### 调用与业务处理

| 类 | 职责 |
| --- | --- |
| `OrderIdGenerator` | 由 caller service 持有，为该 service 发起的所有新订单生成统一 `OrderId`。 |
| `TradingClient` | 调用方使用的交易接口，提供报单、撤单和同步查询。 |
| `TradingListener` | 接收请求失败、委托、撤单和成交回报；回报携带原始请求的账户与归属。 |
| `LocalTradingClient` | 直接调用本地 `TradingService`，查询 service 中的订单和账户状态。 |
| `TradingServiceRegistry` | 保存本地 service ID 到 `TradingService*` 的注册关系。 |
| `TradingClientFactory` | 使用注入的实例表创建 client；跨进程阶段再接入部署拓扑。 |
| `TradingService` | 按账户选择接入对象，通过接入回调更新订单和账户状态，向调用方交付回报；`Run()` 推进需要延迟执行的工作。 |

`main` 创建具体对象、绑定账户与接入对象、建立 service 注册关系，再向 factory 注入实例表。container 只调用 `Service::Run()`，业务实例寻址由对应实例表负责。

### 柜台接入与模拟场所

| 类 | 类型 | 职责 |
| --- | --- | --- |
| `ITradingAdapter` | 接口类 | 一个账户的柜台接入接口，发送交易请求，通过注册的 Callback 交付回报。 |
| `ITradingAdapterCallback` | 回调接口类 | 以只读引用接收柜台回报，由账户上下文转交 service 处理。 |
| `SimulatedTradingAdapter` | 接口实现 | 保存一个模拟账户的委托，处理报撤单，按验证场景产生交易事件并控制交付时机。 |
| `SimNowTradingAdapter` | 接口实现 | 绑定一个实际交易账户，负责接入库调用、柜台标识关联和回调线程到业务线程的数据交接。 |

`SimulatedTradingAdapter` 和 `SimNowTradingAdapter` 实现 `ITradingAdapter`。`main` 为每个账户创建对应的接入实例，在运行前绑定到 `TradingService`。模拟接入实例保存本账户的委托；需要延迟交付的回报由该实例保留到交付时。

### Service 内部对象

| 结构 | 保存的内容 |
| --- | --- |
| `AccountContext` | 账户标识、借用的 adapter 指针及账户状态；实现 `ITradingAdapterCallback`，将回报连同绑定账户交给 service。 |
| `OrderRecord` | 统一 `OrderId`、原始订单参数、账户与策略归属、订单状态、成交数量、调用关联信息及回报接收方。 |
| `CancelRecord` | 撤单请求标识、目标订单、撤单处理状态、调用关联信息及该请求的回报接收方。 |

这些结构由 `TradingService` 管理。订单数量和状态由同一份 `OrderRecord` 提供给查询与回报处理。`OrderRecord` 保存可变的当前状态；`OrderSnapshot` 在查询或通知时复制生成，不作为内部状态存储。

## 标识与数据契约

YQuant 自行生成的序号和请求标识（如 `sequence`、`cancel_request_id`、`service_cancel_id` 和 `call_id`），当前在各自作用域内保证单次运行期间不重复。N13 持久化标识生成状态，并明确作用域标识在重启后的延续规则，使同一作用域在进程重启后也不复用已分配的标识。正常退出和异常退出均需满足这一要求，具体机制在 N13 的持久化恢复中细化。

### 订单标识

YQuant 内部使用 caller 生成的统一 `OrderId`。该标识在 client、service、adapter 和回报之间保持不变。

```text
OrderId = (caller_service_id, sequence)
```

| 标识 | 含义与作用范围 |
| --- | --- |
| `caller_service_id` | 生成订单标识的 caller service ID，在部署中全局唯一。 |
| `sequence` | caller service 在本次运行期间生成的单调递增序号。 |
| `order_id` | 由上述两字段组成，在首版单次运行范围内唯一。 |
| `account_id` | 目标 TradingService 管理的账户，由组装层绑定到接入对象。 |
| `strategy_id` | 在调用方 service 内标识策略实例。 |
| `counter_order_id` | 柜台订单标识，类型名为 `CounterOrderId`。由具体 adapter 处理完整的账户和会话作用范围，并与统一 `OrderId` 关联。 |

一个 caller service 持有一个 `OrderIdGenerator`，所有策略、账户、client 及目标 TradingService 共用它分配序号。生成器在调用方业务线程内使用，每次新报单消耗一个序号；序号不因发送失败、切换账户或切换策略而复用。序号耗尽时生成失败，不允许回绕。

```text
caller service 100：生成 (100, 1)、(100, 2)、(100, 3)
caller service 200：生成 (200, 1)、(200, 2)、(200, 3)
```

不同 caller 可以独立使用相同序号，完整 `OrderId` 仍然不同。账户和策略是订单归属字段，不参与 `OrderId` 的生成；调用方 service ID 直接从 `OrderId` 取得。

每个 TradingService 对自己接收的完整 `OrderId` 查重。同一 ID 换账户或策略再次提交，也不能建立第二笔订单或覆盖原记录。跨目标 TradingService 的 ID 唯一性由 caller 的共享生成器保证。

caller 重启后，存活的 TradingService 仍按本次运行已保留的订单查重。

adapter 接收报单时即取得 `OrderId`，并建立与柜台请求及 `CounterOrderId` 的关联。即使柜台尚未分配 `CounterOrderId`，早期回报也必须能携带原始 `OrderId`。`CounterOrderId` 的底层表示与长度由接入实现处理。

每次撤单还带有独立的 `cancel_request_id`，在目标 `OrderId` 内唯一。TradingService 为 adapter 调用分配 `service_cancel_id`，用于关联多次撤单尝试的结果。

每次报单或撤单调用还生成内部请求关联标识 `call_id`，在该 client 实例内唯一。client 实例标识与 `call_id` 随内部调用上下文传递，保存在订单记录和内部通知中；跨进程时随响应封装传回，用于定位本次调用的 listener。即使两次提交使用同一 `OrderId`，也能把重复请求的失败交付给第二次调用。该关联标识由 client 管理，不放入业务回报；调用方使用统一的订单标识和自己的撤单请求标识。

### 成交标识

`TradeId` 由 `venue`、`session`、`value` 三个字符串组成：分别标识柜台市场、成交编号的复用作用域（例如交易日）和柜台成交编号。三个字段均非空，保留完整内容；实际接入负责将柜台的唯一性字段无损映射到这些字段。账户作为外层作用域，各账户独立维护成交哈希表；同一市场在不同作用域中复用编号属于不同成交。

### 请求与回报数据

领域模型独立于服务请求：通用币种类型 `model::Currency` 定义在 `model/currency.h`，订单、成交、资金和持仓模型分别定义在 `order.h`、`trade.h`、`funds.h` 和 `position.h`，请求及业务回报数据定义在 `trading_service.h`。

- `OrderInfo` 保存 `order_id`、`account_id`、`strategy_id` 和合约、方向、开平、价格、数量及套保类别 `hedge` 等原始委托参数。
- `SubmitOrderRequest` 通过 `order` 字段携带一份 `OrderInfo`。
- `CancelOrderRequest` 包含目标 `order_id`、账户、策略及调用方撤单请求标识。
- `QueryOrderRequest` 包含目标 `order_id`、账户和策略，用于定位订单并核对归属。
- `QueryFundsRequest` 包含目标账户；同一账户的各策略读取共享的资金状态。
- `QueryPositionsRequest` 包含目标账户；`QueryPositionRequest` 另带持仓键，用于单项查询。
- `OrderSnapshot` 通过 `order` 字段保存一份 `OrderInfo`，另含当前状态、累计成交数量和单调递增的状态版本，不保存服务请求对象。
- `RequestFailure` 表达某次已交付请求的处理失败，包含 `order_id`、错误码 `reason` 和可选的订单快照 `snapshot`。校验失败没有快照；已建立订单或已通过撤单校验后的发送异常携带订单快照。撤单失败另带本次 `cancel_request_id`，见撤单处理规则。
- `OrderReport` 通知订单状态的变化，例如委托接受、委托拒绝和订单撤销。
- `CancelReport` 表达某次撤单的结果，并关联原订单及撤单请求。
- `TradeInfo` 保存原始订单 ID、完整成交标识、成交价格和数量；账户来自 adapter 的绑定上下文。
- `TradeReport` 通过 `trade` 携带一份成交明细，通过 `snapshot` 携带合并后的订单快照。
- `model::Currency` 统一表示币种，负责三个大写字母代码的构造、校验、比较和读取；默认值及非法输入产生未指定币种。
- `FundsInfo` 使用 `model::Currency` 表达币种，保存该币种下的不含浮动盈亏的账面权益 `balance`、扣除已占保证金但尚未扣除本地委托预占的 `available`、占用保证金 `margin` 和委托预占中的保证金部分 `frozen_margin`。币种须有效，金额须有限；adapter 将初始柜台数据转换为该记账口径。
- `FundsSnapshot` 保存本地 `FundsInfo`、初始基准轮次 `refresh_id`、委托预占合计 `reserved`，以及初始化以来已入账手续费 `commission` 和已实现盈亏 `realized_pnl`；`available_for_orders()` 返回 `available - reserved`，不再额外扣除已包含在预占中的 `frozen_margin`。
- `FundsTerms` 保存一个账户、合约和下单方向的币种、合约乘数、按金额和按手数计收的开仓保证金及各开平类型的费率；`FeeRate` 包含按数量费用与按名义金额费率。缺少费率与明确零费率分别表达。
- `PositionKey` 由合约标识、持仓方向 `PositionSide` 和套保类别 `HedgeFlag` 组成；区分多仓与空仓，以及投机、套利和套保持仓。
- `PositionInfo` 保存持仓键、今仓与昨仓数量、冻结数量，以及各自的可选 `PositionCost`。`PositionCost` 保存以账户币种计价、已含合约乘数的总成本与占用保证金。非空持仓必须提供有限正成本及有限非负保证金；空仓可省略成本，提供时两项必须为零。
- `PositionsSnapshot` 通过只读连续视图借用完整账户持仓，携带已发布轮次 `refresh_id`；有效空快照的行数为零。行数据有效至下一次持仓更新或所属 service/cache 销毁，需要长期保留时复制。

请求参数只借用到调用返回；接收方复制后续处理所需的数据。回报参数只借用到回调返回，调用方需要长期保留时复制快照。

订单相关业务回报保留原始 `OrderId`，并与本次处理产生的订单快照一同交付，远端 client 应用 service 计算的状态。重复 `OrderId` 等请求校验失败只产生本次调用的失败回报，不修改已有订单，也不携带用于覆盖原订单的状态快照。

### 接入异常处理

adapter 负责外部柜台的数据转换和标识关联，Trading 负责校验接入事件并执行相应的业务处理。处理规则覆盖请求发送、订单及成交回报、账户快照和连接状态；每类异常明确状态变化、业务通知、查询可用性与后续处理，并通过可控接入事件验证。各交易接口的失败和回报处理随 N2 验证，N5 补齐实际柜台事件的转换；账户接入异常及跨场景验收见 [N13.2](../plans/v1.md#n132异常接入事件处理与综合验收)。

Trading 保留已经确认的订单事实。发送成功且尚无有效柜台回报时，订单保持 `kSent`；回报缺失或连接中断不能直接认定委托被拒绝、撤单成功或订单已经结束，也不能自动重报已经发出的请求。发送返回与后续回报不一致时，按有效回报核实实际委托结果，异常处理见报单处理规则。

无法关联、账户不符、字段非法或内容矛盾的事件，需要有明确的处理与诊断，不能误关联或污染已有订单。接入可用性按账户维护；N13 负责断连时保留本地状态，重新连接后核实订单、资金和持仓；账户完整性未确认前不恢复新报单。一个账户的接入异常不改变其他账户的有效状态。

### 报单处理规则

`sequence` 从 1 开始；合约标识和数量必须为正，价格必须为有限正数，方向和开平值必须属于接口枚举。账户与策略标识按原值保存，不依赖全局递增顺序。

| 场景 | 已知事实与状态 | 业务通知与后续处理 |
| --- | --- | --- |
| 未绑定账户、重复完整 ID、非法参数 | 本次请求未建立订单，已有订单保持原值 | 请求已交付后，在调度阶段向本次调用的 listener 交付校验失败，不带订单快照。 |
| 确定未发送，且没有有效柜台回报 | 已建立记录转为发送失败 | 交付发送阶段的请求失败及快照，保留记录供后续查询。 |
| 已发送，尚无柜台回报 | 保存已发送状态，接受或拒绝尚待回报 | 不以发送成功替代委托回报；后续回报使用原始 ID。 |
| 发送失败后迟到有效委托回报 | 柜台事实修正此前发送判断，更新为接受或拒绝 | 诊断发送判断与后续回报不一致，保留早先失败通知的快照，再按顺序交付新的委托回报。 |
| 接受或拒绝回报重复 | 已确认状态不变，版本不增长 | 不重复通知。 |
| 未知 ID、错误账户、非法回报状态或接受与拒绝互相矛盾 | 不应用异常事件，保留已确认状态 | 向 stderr 诊断；不伪造订单结果，等待有效信息。账户断连与可用性在 N13.2 扩展，运行中核实与恢复由 N13 交付。 |

柜台接受或拒绝由 `OnOrderReport` 表达。发送失败后若迟到有效柜台回报，诊断发送判断与回报不一致，再按柜台事实更新订单；已交付失败通知中的快照保持不变。

每次对外状态或累计成交量变化递增版本，重复与无效事件不递增。延迟通知保存当时快照；后续有效回报可以产生更高版本。查询读取同一订单记录；发送失败及已发送记录均保留，校验失败不会创建可查询记录。

当前报单实现预留哈希桶，以完整 ID 定位订单；待通知队列使用连续存储的循环队列，交付后立即复用槽位，避免调度时搬移剩余通知。新增订单仍需分配哈希节点，队列满时扩容；内存总预算、分配与容量不足处理由 N13.1 完成。

### 撤单处理规则

撤单请求携带原始 `OrderId`、账户、策略和非零 `cancel_request_id`。服务先核对订单及归属，再检查订单可撤销性及撤单 ID；同一订单已经建立的撤单 ID 不复用，包括发送失败的尝试。订单处于 `kSent`、`kAccepted` 或 `kPartiallyFilled` 时允许尝试撤单；发送撤单不改变订单状态。

每次已建立的尝试分配本服务内单调递增的 `service_cancel_id`，耗尽时失败且不回绕。adapter 按绑定账户、原始订单 ID 及该服务撤单 ID 发送请求，回报完整保留二者。服务按服务撤单 ID 定位尝试，再核对来源账户与订单，避免迟到回报完成其他尝试。

| 场景 | 订单与撤单记录 | 通知与后续处理 |
| --- | --- | --- |
| 未知订单、归属不符、订单不可撤、重复撤单 ID 或非法 ID | 不建立本次撤单记录，不改变订单 | 向本次调用的 listener 交付 `RequestFailure`，带订单 ID 和本次撤单 ID，不带快照。 |
| 服务撤单序号耗尽 | 不调用 adapter，不建立尝试 | 请求已经交付，后续通知 `kIdExhausted`。 |
| 确定未发送 | 保留本次尝试与原订单状态 | 交付带当前订单快照的发送失败通知；调用方下次尝试使用新撤单 ID。 |
| 已发送 | 本次尝试等待柜台结果，订单状态保持原值 | 请求返回前不通知业务 listener，后续通过 `OnCancelReport` 交付结果。 |
| 柜台拒绝 | 完成本次尝试，保留当前订单状态 | 向撤单 listener 交付拒绝结果及当前快照。 |
| 柜台确认撤销 | 完成本次尝试，将活动订单更新为 `kCanceled`，保留成交数量 | 先向原订单 listener 交付状态变化，再向本次撤单 listener 交付成功结果，两份通知使用本次事件的独立快照。 |
| 撤单结果前已全部成交 | 完成本次撤单尝试，保留 `kFilled` 与成交数量 | 撤单 listener 仍收到本次结果，不重复通知订单状态。 |
| 发送失败后迟到有效回报 | 诊断发送判断与回报不一致，再按有效回报处理本次尝试 | 已通知的失败快照不变，后续结果仍关联原撤单 ID，不自动重报。 |
| 重复、冲突或错误关联的回报 | 相同结果不重复通知；冲突结果、未知尝试、账户或订单不符及非法枚举均不应用 | 输出诊断，保留已有订单事实。另一次尝试已经撤销订单时，本次拒绝只结束自身尝试，不回退订单状态。 |

`RequestFailure` 使用可选的 `cancel_request_id`：报单失败为空，撤单失败携带本次请求 ID。撤单发送失败的快照反映订单本身；撤单尝试的结果由撤单 ID 和错误码表达，不将订单标记为报单发送失败。柜台撤单回报通过 `CancelReport` 携带原始订单 ID、调用方撤单 ID、结果及订单快照。

adapter 的 `CancelOrder` 与 `SubmitOrder` 都不得在调用期间触发 Callback。模拟接入保存委托状态，撤单结果在后续 `Run()` 中交付，并按同一个批量上限处理委托与撤单回报。各项记录与索引的容量控制沿用 N13.1 的统一预算方案。

## 接口

### TradingClient

关键签名：

```cpp
RequestResult SubmitOrder(const SubmitOrderRequest& request,
                          TradingListener& listener);
RequestResult CancelOrder(const CancelOrderRequest& request,
                          TradingListener& listener);
bool QueryOrder(const QueryOrderRequest& query, OrderSnapshot& snapshot) const;
bool QueryFunds(const QueryFundsRequest& query, FundsSnapshot& snapshot) const;
bool QueryPositions(const QueryPositionsRequest& query,
                    PositionsSnapshot& snapshot) const;
bool QueryPosition(const QueryPositionRequest& query,
                   PositionInfo& position) const;
```

`RequestResult` 表达请求是否进入当前调用路径：

- 未交付：调用方立即得到失败原因，本次请求不再产生回调。当前本地 client 在实例标识或调用序号耗尽时返回 `kIdExhausted`，不复用旧标识。
- 已交付（`kDelivered`）：后续处理结果通过回报交付，包括服务校验失败、柜台发送失败、柜台接受或拒绝。

本地路径将请求交给 service，跨进程路径将请求交给消息通道；成功返回均不代表柜台已经接受委托。服务侧处理失败由错误码表达原因；柜台拒绝通过委托回报交付。

`SubmitOrder` 和 `CancelOrder` 返回前不调用业务 listener。adapter 的 `SubmitOrder` 调用期间不得触发任何 Callback；柜台 SDK 在调用期间产生的回报先保存，由后续 `Run()` 交付。service 将校验失败和发送失败的通知排队，由请求返回后的调度阶段交付。同一订单已有待通知回报时，后续回报也排队，保持该订单的通知顺序；其余业务线程回报直接处理并通知 listener。

`QueryOrder` 按 `OrderId` 定位订单并核对请求中的账户和策略。记录可用且归属匹配时返回 true 并写入快照；否则返回 false，保持输出参数不变。本地 client 读取 service，远端 client 读取已经建立的本地缓存。

`QueryFunds` 按账户读取最近可用的资金及本地预占，返回 true 并复制结果；账户未知或资金不可用时返回 false，保持输出参数不变。查询读取启动基准与交易事件形成的本地状态，更新与预占规则见[账户资金](#账户资金)。

`QueryPositions` 返回 true 并借用账户的完整持仓视图，包括有效空持仓。`QueryPosition` 返回 true 并复制指定持仓；完整视图中不存在的合法持仓键返回该键及零数量。账户未知、持仓不可用或单项查询键非法时，查询返回 false，保持输出参数不变。更新规则见[账户持仓](#账户持仓)。

### TradingListener

```cpp
void OnRequestFailure(const RequestFailure& failure);
void OnOrderReport(const OrderReport& report);
void OnCancelReport(const CancelReport& report);
void OnTradeReport(const TradeReport& report);
```

各次请求失败交付给对应调用的 listener。`SubmitOrder` 的 listener 接收该订单的委托和成交回报；`CancelOrder` 的 listener 接收该次撤单请求的结果。撤单导致订单状态变化时，订单 listener 同时收到相应的订单回报。

服务校验失败或确定未发送通过 `OnRequestFailure` 通知；柜台接受或拒绝委托通过 `OnOrderReport` 通知。已经建立订单后确定发送失败时，失败回报同时携带对应状态快照，供 client 更新查询视图。账户可用性的通知与查询表达随对应功能节点细化。

回调前先更新订单状态。回调中可以提交新请求或查询订单；请求调用、回报交付或 `TradingService::Run()` 正在执行时，再次调用 `Run()` 直接返回。当前回调使用独立快照，回调内操作其他请求不会改变正在读取的回报内容。查询读取最近已处理的状态，可能比延迟交付的回报快照更新。

当前静态组装下，listener 的生命周期覆盖 service 的整个运行期。订单进入终态后仍可能交付此前成交的明细，listener 不以某一条终态回报作为销毁依据。

### TradingService 与账户绑定

```cpp
bool BindAccount(AccountId account_id, ITradingAdapter& adapter);
bool ConfigureFundsTerms(AccountId account_id, InstrumentId instrument_id,
                         Side side, const FundsTerms& terms);
void Run();
```

`BindAccount` 在初始化阶段建立账户关系，重复账户标识返回失败；同一 adapter 实例只能绑定一个账户。service 创建具有稳定地址的 `AccountContext`，再将其注册为该 adapter 的 Callback。账户归属来自绑定的上下文，接入回调无需通过额外查询确定账户。

`ConfigureFundsTerms` 在组装阶段复制账户、合约及下单方向对应的参数，所有账户在建立第一笔新订单前完成配置；运行、请求及回调期间不修改参数。不存在的账户、非法标识或参数返回 false，不覆盖已有配置。币种必须有效，合约乘数必须有限且为正，已提供的保证金率及费率必须有限且非负；参数允许部分提供，适用参数缺失的订单在检查时失败。

service 借用 adapter。`AccountContext` 的生命周期覆盖所有接入回调；组装层先停止交易请求与调度，并确保接入对象不再调用 Callback，再销毁 service 和接入对象。

service 的报单、撤单及查询入口供本地 client 和后续的 server 适配器使用，调用方通过 `TradingClient` 访问业务能力。

### ITradingAdapter

接口类只声明 `virtual` 函数，具体行为由接入实现提供。关键签名：

```cpp
virtual void SetCallback(ITradingAdapterCallback& callback) = 0;
virtual bool StartAccountSync(std::uint64_t sync_id) = 0;
virtual SendResult SubmitOrder(const SubmitOrderRequest& request) = 0;
virtual SendResult CancelOrder(const AdapterCancelOrderRequest& request) = 0;
virtual void Run() = 0;
```

报单路径复用 `SubmitOrderRequest`，带有统一 `OrderId`、归属和委托参数；`AdapterCancelOrderRequest` 带有目标 `OrderId` 和服务撤单标识。账户由 adapter 实例的绑定关系确定，adapter 事件保留原始 `OrderId`。

`SetCallback` 在初始化阶段注册借用的回调对象。`SendResult` 只包含已发送（`kSent`）和确定未发送（`kNotSent`）；具体柜台返回值的转换规则在实际接入时细化。确定未发送时由 service 产生请求失败回报；已发送时等待柜台回报。发送返回与回调不一致时，遵循接入异常处理规则。

`Run()` 在当前业务线程推进接入对象内部的延迟工作。接入实现使用内部批量上限控制每次处理量，当前没有工作或达到上限时返回；无效或重复输入也计入处理量。`SubmitOrder` 调用期间不得触发 Callback；即使柜台 SDK 同步产生回报，也必须先保存在接入对象中，待 `SubmitOrder` 返回后由 `Run()` 交付。

### ITradingAdapterCallback

```cpp
virtual void OnOrderReport(const AdapterOrderReport& report) = 0;
virtual void OnCancelReport(const AdapterCancelReport& report) = 0;
virtual void OnTradeReport(const TradeInfo& trade) = 0;
virtual void OnAccountSyncReport(const AdapterAccountSyncReport& report) = 0;
virtual void OnFundsReport(const AdapterFundsReport& report) = 0;
virtual void OnPositionsReport(const AdapterPositionsReport& report) = 0;
```

订单与成交回报保留统一 `OrderId`，撤单回报还携带对应的服务撤单标识。资金与持仓回报的账户来自 adapter 的绑定上下文，回报携带各自刷新轮次。所有 Callback 在 service 所属的业务线程调用。回报数据只在回调执行期间有效；adapter 在回调返回后才能复用相应缓冲。

接入状态变化和无法关联到具体订单的异常也需要传给 Trading，对应回调数据与接口随 N13.2 细化。

报单调用返回后，在业务线程产生的回报可以直接通过 `const&` 交付。service 在回调中更新需要长期保存的状态，不要求 adapter 先写入统一事件对象再复制给使用方。

来自其他线程的 SDK 回调在接入边界保存数据，由 adapter 的 `Run()` 在业务线程交付。需要格式转换时，尽量直接写入最终交接存储；交付时借用存储中的回报，Callback 返回后再释放或复用该空间。

## 关键运行流程

### 报单

1. caller 使用所属 service 的共享生成器取得 `OrderId`，将其连同账户、策略及订单参数交给 client。
2. client 将请求交付给 service；service 检查账户、`OrderId`、参数及资金需求，通过后保存订单和 listener，按原始 ID 建立索引并预占账户资金。
3. service 调用对应账户的 adapter 发送请求，调用期间不发生 Callback。adapter 返回已发送时更新为 `kSent` 并保留预占；返回确定未发送时恢复调用前的预占合计，将订单更新为 `kSendFailed`，生成失败通知和订单快照，排队等待调度交付。
4. adapter 通过 Callback 将回报交给对应 `AccountContext`；service 核对账户和订单、更新状态，再按回调时机与订单通知顺序直接交付或保存通知。没有建立订单的校验失败只交付请求结果。

调用 adapter 前建立订单记录；adapter 返回后根据发送结果更新当前状态，后续回报通过原始 `OrderId` 定位订单。非法账户或重复 `OrderId` 的请求失败结果归属于本次调用，不修改原有订单。

### 撤单

1. 按 `OrderId` 定位原订单，核对请求的账户和策略归属，检查撤单请求标识，建立 `CancelRecord`。
2. 使用原订单绑定的账户 adapter 及原始 `OrderId` 发送撤单。
3. 接入回调交付撤单结果时，先关联本次撤单请求，再更新相应订单状态并交付回报。

撤单请求已发送与订单已撤销分别表达。adapter 的 `CancelOrder` 在调用期间不得触发 Callback，结果在后续调度中交付。撤单失败保留订单已经发生的成交和当前状态；撤单成功保留已成交部分，结束剩余委托。

### 成交与状态更新

`AdapterOrderReport.filled_quantity` 表达柜台已成交的累计数量，范围为 0 到原始委托数量；拒绝回报必须为 0。非法数量及已拒绝订单的接受回报诊断后忽略。

订单状态、累计成交和待处理撤单分别保存。撤单期间仍接收成交回报；后到达的接受回报不能把已成交或已撤销订单恢复为活动订单。

累计量为正且小于委托数量时，活动订单进入 `kPartiallyFilled`；达到委托数量时进入 `kFilled`。已撤销订单收到迟到部分成交时只更新数量，全部成交事实优先于已撤销状态。累计回报引起状态或对外累计量变化时递增版本并交付订单回报。

成交明细按账户及完整成交标识去重，内容一致的重复事件不再次累计数量或通知 listener；同一标识内容冲突时，诊断并忽略。对于通过校验的累计成交数量和成交明细，分别记录已报告累计数量的历史最大值与去重后明细总量，订单累计成交量取二者较大值，避免把同一成交计算两次。迟到的较小累计值不能使订单数量回退。adapter 负责将柜台字段转换到这一事件语义。

成交价格须为有限正数、数量须为正且明细总量不得超过委托量。校验失败、错误账户、未知订单及已拒绝订单的成交均诊断后忽略，不消耗成交标识。发送失败后收到有效成交时，诊断发送判断与柜台事实不一致，再更新订单。

每笔有效的新明细只向原订单 listener 交付一次 `OnTradeReport`，不额外交付相同变化的 `OnOrderReport`；回报带有更新后的快照。累计回报已使订单全部成交时，补到的唯一明细仍须交付，但对外状态与数量没有变化就不递增版本。

每个接入事件先核对来源账户、订单关联及数据有效性。通过校验后更新订单记录，生成回报快照并通知对应 listener；异常事件走对应处理路径。回调内查询能够看到已应用本次有效事件的订单状态。

### 多账户调度

`TradingService::Run()` 先按内部批量上限交付待通知回报，再依次调用各账户 adapter 的 `Run()`，每个账户调用一次。adapter 自行限制本次处理量，通过 Callback 交付回报。某个账户或待通知队列持续有工作时，其他账户仍能在本轮得到推进。

```text
按批量上限交付待通知回报
遍历每个账户：
    调用 adapter.Run()
    在 Callback 中接收并处理回报
```

待通知队列保存 service 产生的请求失败结果，以及因请求调用或同一订单仍有待通知回报而需要延迟交付的业务回报。需要排队时，保存该次通知内容和当时状态快照，连续产生的接受、成交等通知保持原顺序。交付已保存通知时不重复更新订单状态。

### 账户资金

程序启动时，每个账户与柜台同步一次资金和完整持仓，建立本地基准后进入交易状态。后续运行期间，报单、发送结果、拒单、撤单及成交驱动本地资金和持仓更新；查询读取本地状态。启动同步及回报衔接由 N2.10 实现，运行中对账和持久化恢复由 [N13](../plans/v1.md#n13运行中对账与持久化恢复) 实现。

每个 `AccountContext` 保存初始资金基准、本地交易调整及可用性。查询通过已有账户哈希索引定位，资金状态使用定长值，读取与发布无需动态分配。同一账户的多个调用方读取同一份视图。委托预占按账户聚合，成交记账复用持仓键的哈希索引和原订单记录；查询无需遍历订单。首次出现的持仓键才增加行及索引，已清空的行保留供后续成交复用。

有活动挂单的账户按[恢复挂单的本地记账](#恢复挂单的本地记账)交付整份恢复基准。分开交付资金和持仓时，资金使用 `AdapterFundsReport` 事件：`FundsRefreshStarted`、完整的 `FundsInfo` 或 `FundsRefreshFailed`。service 在首次 `Run()` 调用 `StartAccountSync(sync_id)`，资金与持仓事件共用该次请求的非零递增 ID。请求返回 false 或收到失败结果后，由组装层调用 `RetryAccountSync(account_id)` 调度下次尝试，运行循环不自动反复重试；adapter 收齐所有字段后交付完整结果。成功建立基准后，不再发起资金查询，迟到或意外快照不能覆盖本地交易状态。

| 启动同步事件 | 资金视图与查询结果 |
| --- | --- |
| 尚未收到完整有效资金 | 查询不可用，输出参数保持原值；有效零资金须由完整结果建立。 |
| 开始较新初始化尝试 | 取代此前未完成轮次；保留已收到的数据，不提前报告交易就绪。 |
| 当前轮次交付完整有效资金 | 保存初始基准；资金、持仓与完成确认均到齐后开放两类查询并进入交易状态。 |
| 当前轮次失败、中断或值非法 | 标记未就绪，诊断原因，允许启动阶段重试。 |
| 旧轮次、重复结果或零轮次 ID | 不改变基准及可用性，非法事件输出诊断。 |
| 进入交易状态后收到初始化结果 | 忽略并按需诊断，保留本地交易更新。 |

启动全量状态重建由 [N5.2 至 N5.8](../plans/v1.md#n52启动资金与持仓快照) 扩展实现。每次重启从柜台拉取订单、成交、资金与持仓，建立活动订单、标识及资金和持仓冻结的关联，不依赖本地持久化状态；不能以有历史挂单或冻结非零作为初始化失败条件。

启动完成确认需要覆盖完整初始状态及同步期间的回报衔接。已经包含在快照中的成交不重复应用，尚未包含的变化不遗漏；历史挂单的剩余冻结延续到后续成交或撤单，不再重复建立一份预占。订单重建后继续接收回报，未归属订单按柜台标识独立记账；策略按[启动边界与挂单接管](#启动边界与挂单接管)绑定已有挂单。数据不完整或关联无法核实时保持未就绪并支持启动重试，运行中对账及持久化恢复由 N13 处理。

目标 `TradingService` 按账户维护统一资金记录，本地与远端调用方共用。资金需求使用委托价和组装层提供的参数计算：

```text
名义金额 = 委托价 × 数量 × 合约乘数
预计手续费 = 按数量费用 × 数量 + 按名义金额费率 × 名义金额
开仓预占 = 名义金额 × 保证金率 + 数量 × 每手保证金 + 预计手续费
平仓预占 = 预计手续费
```

按下单开平类型选择相应费率，平仓不提前计入保证金释放。开仓须有保证金率，每种报单须有对应手续费参数；未知参数不能当作零费用。币种不匹配、资金不可用、所需参数缺失、资金不足或计算结果无法表示时，向本次调用方交付失败，不调用 adapter，也不建立订单或改变已有预占。已知零资金需求不增加占用。

资金检查在调用 adapter 前完成。预占合计保存在账户上下文，每笔金额保存在原订单记录，通过已有索引关联；重复 ID 及其他校验失败不产生新预占。确定未发送时，利用单业务线程及 adapter 调用期间无回调的约束，恢复发送前的预占合计，避免反复加减产生残差；已发送而尚未确认的订单继续保留占用。失败通知在请求返回后交付，回调中可以重新提交新 ID 的订单。参数表在初始化时预留哈希桶，资金检查通过合约与方向的键定位，不创建额外临时容器。

柜台拒单时释放未使用预占；发送撤单及撤单失败保留占用。撤单成功回报携带最终累计成交量，先与已知成交量合并，再释放未成交部分；成交明细晚到时不会提前释放该部分预占。同一撤单尝试重复报告不同的最终成交量时，保留已收事实并将账户数据标记不可用，交由 N13 核实。已知成交但尚无明细的部分保留原估算，明细到齐后才转换为实际占用和费用。原始预占按订单保留，发送失败后迟到接受回报可恢复预占；迟到成交照实记账，不因先前释放而漏记。没有回报或连接中断不构成释放依据。

成交记账按账户、合约、持仓方向及套保类别维护今仓、昨仓两个成本桶。开仓成交增加今仓总成本和保证金；平仓按被平数量占该桶数量的比例分摊成本和保证金，最后一笔取尽余量。昨仓成本采用已经反映在启动账面权益中的结算基准，今仓采用开仓成交成本。adapter 必须保证初始资金和成本基准一致，浮动盈亏不通过本节点的行情输入重估。

```text
成交金额 = 成交价 × 合约乘数 × 成交数量
开仓：保证金变化 = 成交金额 × 保证金率 + 成交数量 × 每手保证金，已实现盈亏 = 0
平仓：分摊成本 = 桶总成本 × 平仓数量 / 桶数量
      保证金变化 = -桶保证金 × 平仓数量 / 桶数量
      多仓盈亏 = 成交金额 - 分摊成本，空仓盈亏取反
手续费 = 按数量费用 × 成交数量 + 按名义金额费率 × 成交金额
账面权益变化 = 已实现盈亏 - 手续费
可用资金变化 = 已实现盈亏 - 手续费 - 保证金变化
```

`kCloseToday`、`kCloseYesterday` 只使用指定桶；通用 `kClose` 默认先昨后今，`FundsTerms::close_today_first` 可配置为先今后昨。N5 需将该规则与实际柜台平仓分配口径对应。手续费按原请求的开平类型计收。

唯一成交明细按 adapter 交付顺序入账，累计数量回报只更新订单事实，不按委托价猜测成交价。adapter 应保持不同成交明细的来源顺序；订单、撤单与成交明细之间的交错及重复交付不重复记账。账户存在已知成交数量大于已记账数量的订单时，资金及持仓查询返回不可用，新报单失败；明细补齐后恢复，订单查询和回报继续正常交付。

成本与资金先在栈上的候选值中计算，全部校验通过后一起发布，再交付业务回调。持仓不足、数据无法计算或金额无法表示时保留订单及成交事实、输出诊断，并标记账户数据不可用；差异恢复由 N13 处理。保证金释放若仅产生一个浮点表示步长内的负残差，则归零；更大的负值作为记账异常。

N2.11 完成本地成交记账与预占调整；交易结果无法确定时保留占用和诊断。运行中订单、资金、持仓与柜台的核对、快照覆盖关系及差异恢复统一在 N13 设计和实现。

### 账户持仓

同一账户的策略共享完整持仓及可用性。账户持仓以连续行存储支持遍历，另以完整 `PositionKey` 建立哈希索引，支持高频单项查询；两个查询接口均不分配内存。本地持仓区与初始化暂存区分开，账户初始化时预留空间，初始同步成功后交换两组存储，失败重试复用容量。条目数超过预留容量时，初始化暂存区按需扩容。

`AdapterPositionsReport` 通过 `event` 携带开始 `PositionsRefreshStarted`、持仓行 `PositionInfo`、完成 `PositionsRefreshCompleted` 或失败 `PositionsRefreshFailed`。`refresh_id` 在本账户的初始化尝试之间非零、递增且不回绕，与同次资金初始化使用相同请求 ID。

adapter 将柜台明细按持仓键整理为一键一行，今仓、昨仓、冻结量和各自成本及保证金写入同一行。完成事件的 `expected_count` 是本轮唯一标准化条目数，在接入侧完成数据整理后、交接前确定；service 将已收唯一行数与之核对。接入无法确认数据完整性时交付失败，不能以缺失数据构造空快照。

| 启动同步事件 | 持仓视图与查询结果 |
| --- | --- |
| 初始数据尚未完整 | 查询不可用，输出参数不变。 |
| 开始较新初始化尝试 | 清空暂存区并取代此前未完成轮次。 |
| 当前轮次收到有效行 | 按键保存到暂存区，不暴露部分快照；内容相同的重复行忽略。 |
| 当前轮次完成且唯一行数匹配 | 建立完整持仓基准，零条目建立有效空持仓；与资金及同步期间回报衔接完成后进入交易状态。 |
| 行非法、同键冲突、计数不符或失败 | 关闭本轮并标记未就绪，诊断后允许启动阶段重试。 |
| 旧轮次、已关闭轮次或零轮次 ID | 不改变当前数据及可用性，非法事件输出诊断。 |
| 进入交易状态后收到初始化结果 | 忽略并按需诊断，不覆盖本地交易更新。 |

每个持仓键分别维护今仓、昨仓的可平数量：各桶的可平量等于持仓量减去冻结量，通用平仓可使用两桶之和。卖平使用多仓，买平使用空仓；不同账户、合约和套保类别不共用持仓。

资金校验通过后，service 按订单开平类型和当前可平量分配平仓数量。平今、平昨只使用指定桶；通用平仓先用配置优先桶中的可平量，不足部分再从另一桶分配。数量不足返回 `kInsufficientPosition`，不建立订单、不预占资金、不调用 adapter。通过校验的订单在发送前同时取得持仓冻结和资金预占。确定未发送或柜台拒单时释放本单冻结；撤单请求和撤单失败保留冻结。

订单保存提交时的今昨仓分配。即使其他策略先成交或增仓，本单的成交仍从原分配中依次扣减持仓和冻结，资金记账也使用相同分配。撤单成功时只释放未成交部分；最终累计成交量中尚无明细的部分继续冻结，明细到齐后只扣一次。可用资金或成交数量无法确定时，账户查询不可用，新平仓不发送。缺少回报不释放冻结。

发送失败后迟到的接受回报按原分配恢复冻结；迟到成交先核对所需的原桶数量，再更新持仓和成本。若原桶可平量已被其他订单占用，保留订单与成交事实，输出 `close_hold_unresolved` 并停止使用该账户数据，交由 N13 核实。N5 接入需要验证通用平仓的实际分配与本地口径一致。

冻结与查询复用账户的持仓键索引；订单保存稳定的行索引和桶分界数量，处理回报时无需遍历其他订单。持仓视图在下次持仓更新或销毁前有效。

## 订单存储与生命周期

账户表以连续存储保存稳定账户上下文的指针或索引，供 `Run()` 遍历，另建账户标识索引供请求定位。已注册为 Callback 的 `AccountContext` 地址保持稳定。订单存储以统一 `OrderId` 建立索引，查重、撤单、回报和查询均通过该索引定位。账户及策略归属保存在记录中，定位后再核对。查询和回报路径使用同一份订单状态。

本次运行期间建立的全部订单需要可查询，包括终态订单及已建立记录后发送失败的订单。订单链路的内存使用必须有明确上限，预算覆盖订单及索引、资金预占、持仓冻结及未确认记录、撤单关联、柜台标识映射、查重与成交去重信息，以及请求关联、待通知回报和接入交接缓冲。

终态订单的保留方式、内存回收条件和历史查询路径在 [N13.1 订单存储容量管理](../plans/v1.md#n131订单存储容量管理)中细化并实现。回收需要同时考虑待处理撤单、尚未交付的通知和迟到回报，保持订单查重、成交去重及查询契约。未交付或校验失败且没有建立订单的调用，只保留完成本次请求结果所需的临时信息；请求关联与通知数据不再被使用后及时释放。

存储按预算预分配并复用，必要的扩容受预算约束。`OrderId` 与存储槽位分离，保留 caller 生成的原值。回调读取事件快照，不暴露内部记录地址；快照仍被使用时，对应存储不能回收或覆盖。

接受请求前保证有足够存储保存请求及其结果，并为已接收订单的后续回报处理保留空间。本地 service 无法接收时，client 返回未交付；跨进程请求已经交付消息通道后，service 拒绝接收的结果由 server 转为 `RequestFailure`，关联原调用并通知 listener。容量不足不能通过覆盖已有记录或静默丢弃回报处理，回收出足够空间后恢复接收。

client 由创建它的调用方持有；实例表和 factory 用于初始化，可以先于已经创建的 client 销毁。service 在 client 和业务回报处理结束后销毁，adapter 的有效期覆盖 service。

## 模拟场所与扩展

### 可控验证

`SimulatedTradingAdapter` 接收报撤单并维护本账户的模拟委托。验证场景可以控制发送结果、委托接受或拒绝、撤单结果，触发指定价格和数量的成交，并控制回报的释放时机和交错顺序；同时支持注入异常字段、重复或矛盾回报、回报缺失及连接状态变化，验证 Trading 的处理规则。

`Fill(const TradeInfo&)` 在模拟柜台中验证活动订单、成交字段、重复标识与剩余数量，成功时保存独立明细并排队，失败时返回 false 且不改变柜台。`EmitTrade` 供验证场景直接注入迟到或异常明细，不改变模拟柜台状态。

`QueueFunds(const AdapterFundsReport&)` 复制资金事件，按场景排入开始、完整结果或失败事件；也可注入旧轮次及非法值。可以在账户绑定前预置事件，注册 Callback 后由 `Run()` 交付。

`QueuePositions(const AdapterPositionsReport&)` 按相同的交付约定复制持仓事件，支持多条持仓、完成计数、失败以及重复、缺失与轮次交错等验证场景。

`SetInitialState` 配置包含此前历史事件影响的完整模拟基准；`StartAccountSync` 排入该基准和完成结果，存在活动委托或冻结时返回未解决订单结果。未配置基准时，测试通过 `QueueFunds`、`QueuePositions` 和 `QueueAccountSync` 显式控制请求结果及交付顺序。

模拟接入通过注册的 Callback 交付事件，在请求及验证场景的注入调用中只保存数据，由 adapter 后续的 `Run()` 交付；`Emit`、`EmitCancel` 与 `EmitTrade` 供场景直接注入回报。每次最多处理 64 个排队事件，事件共用按入队顺序处理的缓冲。交付前移出当前事件，回调内提交请求导致缓冲扩容时也不会覆盖当前数据。模拟接入可以分别控制发送返回与回调内容，service 先处理发送结果，再处理后续回报。

固定行情继续使用现有行情源。成交由验证场景显式触发，N2 的报单、撤单、成交节点逐步补齐模拟接入能力。

### SimNow 接入

每个账户创建对应的 `SimNowTradingAdapter`，由 `main` 注入同一个 service。接入实现负责登录和交易就绪、原生标识映射及请求转换；报单调用期间产生的回报先保存在接入内部存储，由后续 `Run()` 交付；其他线程的回报也经接入内部存储转到业务线程。client 与业务订单处理使用同一组接口。

#### 交易前置登录

`SimNowTradingAdapter` 在初始化前注册 SPI，订阅私有流与公有流（QUICK）。连接通知到达后，业务线程先发起应用认证，再使用个人模拟账户登录。只有当前请求编号、响应类型和账户匹配的最终成功响应才能推进状态。登录后保存交易日、前置号、会话号及柜台返回的最大报单引用，供后续节点使用。

SDK 线程按回调顺序交付事件，最多允许 32 项待处理控制事件。启动查询的数据行不占控制事件额度。业务线程每次 `Run()` 最多处理一项，不在 SDK 回调内再次调用 API。断连清除登录信息，重连用新的请求编号重新认证；断连前未处理的成功回报不能恢复旧会话。认证或登录被拒、请求未发出、登录超时或队列溢出均结束这次尝试，保留失败原因和柜台错误码。

登录探针在账户组装阶段驱动 adapter，成功时输出 `trader_logged_in ... account_ready=false`。N5.1 不发送资金查询、报单或撤单；账户基准与交易就绪由 N5.2 至 N5.8 建立。接入异常对在途订单及对账恢复的影响在 N13 验收。

在本机环境中设置 `YQUANT_CTP_BROKER_ID`、`YQUANT_CTP_USER_ID`、`YQUANT_CTP_PASSWORD`、`YQUANT_CTP_APP_ID` 和 `YQUANT_CTP_AUTH_CODE`。交易前置地址由账户提供方给出。macOS 交易 SDK 的登录调用另接收终端系统信息；前置需要时，将 `YQUANT_CTP_SYSTEM_INFO_FILE` 指向符合 SDK 要求的终端数据文件。接入按文件内容和实际长度传递，未提供时长度为零；Linux 版使用双参数登录接口。SDK 流文件使用进程当前目录，运行探针时使用独立目录：

```sh
monod_bin="$PWD/build/monod"
flow_dir=$(mktemp -d)
(cd "$flow_dir" && "$monod_bin" --simnow-trader-login "$YQUANT_CTP_TD_FRONT" 30)
```

#### 启动资金与持仓快照

使用同一组登录参数运行 `monod --simnow-startup-snapshot FRONT [SECONDS]`。登录后按账户依次查询资金、全量持仓、委托和成交。当某个合约的同一持仓行同时含今仓和昨仓时，在查询委托前核实该合约的持仓明细。每项查询收到柜台的最终响应后才开始下一项。至少需要一行资金，持仓、委托及成交允许为空。业务线程核验请求编号、账户、交易日、金额及持仓键；相同币种或持仓键重复出现时，整次查询失败。

`StartSnapshot()` 启动一次只读采集。持续调用 `Run()`，直到 `snapshot()` 返回完整结果，或 `snapshot_status()` 报告失败原因。柜台限流时隔一秒重试，整个采集受同一个超时约束。失败后可重新采集，断连后需先重新登录。快照保留柜台口径的可用资金和冻结，以及各持仓行的持仓日期、数量、成本和占用保证金。各次查询间的交易变动由后续启动回报核对处理，交易就绪条件见[账户资金](#账户资金)。

**今昨仓核实。** 今仓数量取 `TodayPosition`，剩余昨仓数量为 `Position - TodayPosition`。只含一种仓龄的汇总行将 `PositionCost` 和 `UseMargin` 计入对应仓龄。混合行触发按交易所和合约查询乘数及持仓明细，同一合约的不同方向、投保属性、投资单元共用这次查询。

明细按投资单元、持仓方向和投保属性分别核对。开仓日期等于当前交易日的剩余持仓按开仓价计算成本，更早的按昨结算价计算，两者均乘合约乘数和剩余手数；占用保证金取各条明细的 `Margin` 之和。今仓、昨仓数量分别与汇总行核对，两个仓龄的成本之和、保证金之和分别与柜台汇总金额核对，允许小于 0.005 个账户货币单位的舍入差。缺少乘数、重复明细、数量或金额不符时，启动快照报告失败原因。成功后从 `SimNowPosition::today_cost` 和 `yesterday_cost` 读取两个仓龄的成本和占用保证金。

#### 委托和成交恢复

启动快照的 `history` 保存柜台对该账户、该交易日返回的全部委托和成交。委托可以按「前置号、会话号、报单引用」查询，也可以按「交易所、柜台订单号」查询。没有柜台订单号的委托保留会话标识。成交按交易所和柜台订单号找到原委托，按交易所、交易日、买卖方向和成交号去重。重复记录内容相同只计一次，标识冲突、成交无对应委托或数据超出委托量时，本轮快照失败。

YQuant 使用带版本的归属标记。编码器将 caller service ID、订单序号和策略 ID 的 192 位原值分成六个 32 位字，按高位在前编码为 30 个 Base85 字符，再加上 `Y1` 前缀。前 20 个字符写入 `BusinessUnit`，后 12 个写入 `OrderMemo`。收到完整且可解码的标记后，恢复原 `OrderId` 和策略归属，并可按 `OrderId` 查询。缺少标记、格式无效或版本未知的订单保留为未归属，仍可通过柜台标识查询。

分配新订单前，caller 取各账户快照中本 caller 的 `LastSequence` 最大值，用它初始化共享的 `OrderIdGenerator`。这覆盖柜台本次返回的历史订单。跨交易日和已离开柜台查询范围的序号由 N13 持久化恢复。发出限价单时将归属标记写入柜台请求。

#### 合约乘数与计费参数

在启动快照命令的超时参数后指定期货合约，例如 `--simnow-startup-snapshot FRONT 30 TF2612`。adapter 在收到完整成交记录后查询合约乘数、品种交易币种、账户投机保证金率和手续费。如果账户保证金是相对费率，继续查询同一合约的交易所保证金作为基准。查询缺行、结果有歧义或费率无效时，命令报告合约及出错项。

快照中的 `terms.buy` 和 `terms.sell` 可分别传给 `ConfigureFundsTerms`。两者使用各自方向的开仓保证金，并限定于投机订单。开仓、平仓和平今手续费分别取对应柜台字段，显式平昨使用平仓手续费。已知零费率保留为零。品种级费率必须匹配合约查询返回的品种代码。

#### 活动委托的冻结核对

启动快照为排队中的限价期货委托逐单关联已有冻结，包括部分成交和未归属的挂单。按交易所、合约、投资单元及投保属性查询适用费率，同一组挂单共用一次费率查询。程序使用限价、未成交手数和买卖方向计算每单的保证金及手续费，按币种分别与 `FrozenMargin` 和 `FrozenCommission` 核对。两项均须相符，非零金额与零不匹配，其余金额允许小于 0.005 个货币单位的舍入差。存在其他冻结资金 `FrozenCash` 时报告无法归属。

卖平挂单核对多仓行的 `ShortFrozen`，买平挂单核对空仓行的 `LongFrozen`，分别按交易所、合约、投资单元和投保属性核对。显式平今、平昨占用指定仓龄。普通平仓单仅在柜台冻结总量、各仓龄持仓数量和其余挂单共同确定唯一分配时接受。对于多笔普通平仓单，即使今昨仓冻结合计吻合，也可能无法确定每单占用的仓龄。

全部核对通过后，`snapshot.holds` 中每条记录以 `order_index` 关联原委托，保存剩余量、币种、保证金、手续费及今昨冻结量。核对失败时保留原始余额、持仓和委托记录，`holds` 为空，`holds_error` 指明原因；可再次调用 `StartSnapshot()` 获取新快照。命令行在核对失败时返回非零退出码。核对期间不调整柜台可用余额或原始冻结总额。

#### 恢复挂单的本地记账

SimNow adapter 用配置中的交易所、合约和本地合约 ID 将已核实快照转换为单币种账户基准。账面权益扣除浮动盈亏；柜台可用资金加回已核实的剩余订单预占后，作为本地扣除预占前的可用资金。每笔活动订单保留自己的计费参数。普通平仓单同时冻结今昨仓时，合约配置必须给出柜台实际扣减仓龄的优先顺序。无法区分同一持仓键下不同投资单元的成本时，账户保持未就绪。

交易服务暂存本轮基准，收到同轮同步边界确认后，核对持仓冻结、各订单的已记账数量及成交去重记录，再一次性安装。缺少已成交明细、订单标识冲突或冻结不符时，整批恢复失败。查询完成本身不能证明同步期间没有发生交易。

恢复订单按账户内柜台标识关联回报。有归属标记的订单另建原 `OrderId` 索引；未归属订单独立记账，不进入策略订单索引，也不向策略发送回调。历史成交只登记去重，后续成交按实际成交价更新费用、保证金和被扣减仓龄的成本。撤单确认只释放未成交余量。若最终累计成交量大于已收到的明细数量，保留待记账部分的占用，明细补齐后恢复资金和持仓查询。

#### 启动边界与挂单接管

账户登录后，adapter 先查询当日完整委托和成交，再读取资金、持仓及所需明细，随后重新查询委托与成交。两次结果按柜台标识比较，行顺序可以不同。委托状态、累计成交量和逐笔成交均须一致，各单的明细总量须与累计量吻合。期间收到本账户交易回报，或两次结果有变化时，重新采集整轮。所有轮次共用一个启动截止时间；已观察到的回报还须在稳定的柜台记录中找到对应事实。同一交易日显式重试时继续核对未覆盖回报。断连、缺少数据、无法关联或超时会使账户保持未就绪。

核对成功后，adapter 交付基准及同轮完成确认；交易服务安装账户和已配置合约的投机报单参数，开放查询及请求。完成后停止启动查询。后续回报按实时事件处理；累计成交先于明细时，资金和持仓等到明细入账后恢复可用。

做市策略在第一笔有效行情到来时，通过交易 client 按 caller、账户、策略和合约查询活动委托，检查每边至多一笔可接管的投机开仓单，再按订单 ID 和状态版本一次性绑定 listener。集合变化、同侧有多个候选或已有其他 listener 时，整组绑定失败，策略暂停报价。成功后沿用已有挂单的标识和价格，同价行情只补缺失的一边。未归属挂单继续独立记账。caller 的共享序号生成器只向前推进，计入可见历史终态订单的序号；跨账户、跨目标服务部署须先汇总该 caller 各启动基准的最大序号，再启动报价。

可控验收运行 `ctest --test-dir build -R '^v1_05_account_startup$' --output-on-failure`。真实前置只读验收使用独立测试程序 `verify_simnow_account_startup FRONT [EXCHANGE SYMBOL]...`，复用交易登录环境变量，在独立流文件目录运行；只有账户就绪且资金、持仓查询成功时才返回 0。

#### 限价报单与委托回报

账户就绪后，交易服务先校验并预占资金及持仓。SimNow adapter 按配置将本地合约 ID 转为交易所和合约代码，向绑定的账户发送当日有效、允许部分成交的限价单。交易方向、开平、投保属性、限价与手数取自原请求。

每次发送前，adapter 将原始 `OrderId` 与 SDK 请求编号、当前会话报单引用关联，并写入归属标记。报单引用从登录返回的 `MaxOrderRef` 与启动快照中本会话已用数值的较大值之后递增。确定未发送也消耗该引用，达到 12 位上限后返回发送失败。SDK 返回零时订单进入已发送状态，非零返回按发送失败释放占用。

SDK 回调复制报单结果，由业务线程在后续 `Run()` 中交付。前置拒单按请求编号关联，未分配交易所订单号的异步错误使用报单引用和归属标记核对。委托回报先按前置号、会话号和报单引用找到本单，再绑定交易所及柜台订单号。重复拒单只释放一次占用；未确认的委托状态继续等待柜台回报。[厂商 Trader API 报单与回调说明](https://www.simnow.com.cn/DocumentDown/api_3/5_2_4/SFIT%2BCTP%2BMini%2BAPI-V1.7.0.pdf)

`ctest --test-dir build -L v1_05_simnow_trading --output-on-failure` 运行全部 SimNow 交易接入可控用例。

### 跨进程调用

跨进程阶段增加 `RemoteTradingClient` 和 `TradingServer`。server 将消息解码为 service 请求，并把回报编码给原调用方；统一 `OrderId`、账户、策略归属和撤单关联标识完整传递。

远端 client 依据调用上下文关联本次请求的 listener，订单缓存按统一 `OrderId` 索引。收到 service 提供的订单快照时，先按状态版本更新缓存，再调用业务 listener；只携带请求失败的回报不改变已有订单缓存。查询读取当前可用的缓存快照。factory 结合拓扑选择本地或远端 client；账户到 adapter 的绑定仍由目标 service 处理。

远端订单缓存和请求关联存储同样受容量预算约束。N9 验证远端缓存回收后的查询可用性，N12 复用这些规则；与服务端容量管理及历史查询的组合验收由 N13.1 完成。

## N2 节点的设计重点

| 节点 | 核心实现与验收重点 |
| --- | --- |
| N2.1 统一订单标识与模拟接入 | 生成统一 ID，模拟接入保存委托，控制发送结果并在后续调度中交付回报。 |
| N2.2 多账户交易 service 报单处理 | 多账户路由、完整 ID 查重、订单状态和通知快照，验证发送失败、迟到回报、回调时机与重入。 |
| N2.3 本地交易 client 与完整报单场景 | 提供 client、factory 与注册表，通过 `monod` 验证完整报单路径和调用关联。 |
| N2.4 撤单与撤单回报 | 在既有订单记录上增加撤单请求关联，使用正确账户和原订单发送撤单，区分撤单结果与订单状态。 |
| N2.5 订单查询与累计成交 | 查询订单及可用性，按累计成交回报更新数量与状态，验证撤单交错及迟到回报。 |
| N2.6 成交明细与去重 | 按完整成交标识去重，合并明细与累计回报数量，验证冲突、越界及终态后补到明细。 |
| N2.7 账户资金查询与更新 | 接入可控的初始资金与后续更新，维护账户查询视图及可用性，验证多账户隔离。 |
| N2.8 账户持仓查询与更新 | 接入初始持仓快照和后续变化，维护持仓查询视图及可用性，验证完整快照与账户隔离。 |
| N2.9 账户资金检查与下单预占 | 统一检查账户资金，发送前建立预占，资金不足时拒绝发送，确定未发送时释放。 |
| N2.10 启动时同步账户状态 | 建立一次资金与持仓基准，处理初始化期间的回报衔接，完成后进入本地记账。 |
| N2.11 订单事件驱动资金调整 | 随拒单、撤单和成交调整占用，处理部分成交及重复、迟到和乱序回报。 |
| N2.12 订单事件驱动持仓调整 | 持仓与平仓冻结随订单、成交事实变化，共享账户统一检查可平数量，处理重复及迟到回报。 |

请求返回语义区分 client 未交付和已交付；adapter 的发送结果区分已发送和确定未发送。请求已经交付后，后续处理结果通过回报表达。具体数据类型和处理分支随对应节点细化，并核对各节点的代码量预算。
